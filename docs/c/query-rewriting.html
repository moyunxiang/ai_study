查询改写与扩展

Query Rewriting and Expansion

也叫：query rewriting　查询改写　query rewrite　query expansion　查询扩展　multi-query　多查询检索　query decomposition　问题分解　伪相关反馈　pseudo-relevance feedback　query reformulation　查询重写　对话式查询改写

在交互版中打开（看它长在树上的哪里）

检索之前先改写用户的问题：补全指代、改成更适合搜索的说法、拆成几个子问题、或者扩展同义词，让检索器更容易找到相关资料。它是检索增强系统里成本很低、效果明显的一步。

先要会：检索与向量数据库

用户的原始问题往往不是好的检索查询：

  • 多轮对话里，“那它的价格呢？”中的“它”指什么，检索器不知道。
  • 用户的说法和文档的说法不同：问“电脑开不了机怎么办”，文档写的是“主机无法启动的排查步骤”。
  • 一个问题包含多个子问题：“比较A和B两家公司去年的营收”需要分别查A和B。

直接拿原句去检索（见检索与向量数据库），召回效果就会打折扣。查询改写在检索前加一步处理。

常见做法。

  • 上下文补全：结合对话历史，把省略和指代补全，“那它的价格呢？”改成“iPhone 16的价格是多少？”。
  • 查询扩展：加入同义词、相关词或缩写全称。经典信息检索里的伪相关反馈（先检索一次，从排名靠前的文档里提取关键词加回查询）就是一种扩展。
  • 多查询：让语言模型从不同角度生成几个改写版本，分别检索，再把结果合并（可以用混合检索里的RRF融合）。
  • 分解：把复杂问题拆成几个子问题依次检索，这和多跳问答的思路一致（见多跳问答）。
  • 抽象化：后退一步提示先让模型提出一个更一般的问题（“这道题涉及哪条物理定律？”），检索背景知识后再回答原问题。
  • 假设文档：HyDE假设文档检索让模型先写一段“假想的答案”，用它的向量去检索。假想答案和真实文档在用词和风格上更接近，往往比问题本身更容易匹配到正确文档，即使假想答案中的事实可能是错的。

在系统中的位置。改写 → 检索 → 重排序（见交叉编码器与重排序）→ 生成（见检索增强生成RAG）。更进一步的智能体式检索（见智能体式检索）让模型在多轮中自己决定下一步搜什么，查询改写成为它反复执行的一个动作；FLARE主动检索则在生成过程中发现自己不确定时，再主动构造查询去检索。

例子

对话历史：“用户：特斯拉Model 3的续航是多少？助手：……”。用户接着问：“那充满电要多久？”

  • 不改写：查询“那充满电要多久？”，检索器可能返回手机、电动自行车的充电文档。
  • 改写后：“特斯拉Model 3充满电需要多长时间”，检索结果集中在正确的车型上。

多查询：同一问题再生成“Model 3 快充 时间”“Model 3 家用充电桩 充电时长”两个版本，三路检索结果合并，覆盖了快充和慢充两种情况。

容易误解的地方

  • 改写本身可能出错：模型把指代补错了对象，后面检索得再好也是错的；改写结果最好能被记录和检查。
  • 每次改写多调用一次模型，增加延迟和成本；简单的单轮查询不一定需要改写。
