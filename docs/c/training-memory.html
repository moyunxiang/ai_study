训练显存的组成：参数、梯度、优化器状态与激活

Where Training Memory Goes

也叫：训练显存　training memory　显存占用　memory footprint　激活值显存　activation memory　激活显存　优化器状态　optimizer states　优化器状态显存　显存不足　OOM　out of memory　CUDA out of memory　显存碎片　memory fragmentation　显存估算

训练时显存被四样东西占用：模型参数、梯度、优化器状态和激活值，另外还有临时缓冲与碎片。前三者随参数量增长，激活值随批大小和序列长度增长，“显存不足（OOM）”时要先弄清是哪一项爆了。

先要会：参数量、计算量与显存 反向传播 显存、内存带宽与“内存墙”

推理一个7B模型只需约14GB存权重，训练它却要上百GB。读懂显存都花在哪，才能判断该用哪种省显存技巧，而不是盲目地调小批大小。

与参数量成正比的三项（混合精度+Adam的常见设置，见参数量、计算量与显存）。

  • 参数：BF16/FP16副本每个2字节，另有一份FP32主权重4字节。
  • 梯度：每个参数2字节（或4字节）。
  • 优化器状态：Adam的一阶和二阶动量各4字节（见自适应学习率优化器）。

合计约每参数16字节。这三项与批大小无关，ZeRO与DeepSpeed和PyTorch FSDP把它们切分到多卡，见分布式训练：数据并行与模型并行。

激活值。反向传播需要前向时各层的中间结果（见反向传播），它们必须一直保存到反向用完。激活显存大致与层数 × 批大小 × 序列长度 × 隐藏维度成正比，注意力分数还额外与序列长度的平方成正比（使用FlashAttention后不再需要存这个平方项）。序列一长、批一大，激活往往比参数还大。序列并行与选择性重计算对Transformer每层的激活量做了逐项估算，并用序列并行和选择性重算把它降下来。

省激活的办法：梯度检查点只存部分层的输入、反向时重算其余；梯度累积用更小的微批；序列并行、上下文并行把长序列切到多卡；把激活卸载到CPU内存，见ZeRO-Offload CPU卸载。

其他开销。CUDA上下文和库本身占几百MB到上GB；临时缓冲（如通信缓冲、矩阵乘的工作区）；以及显存碎片：分配器里空闲的总量够，但没有一块连续的足够大，也会OOM。

排查OOM的顺序。先看是在第一步就OOM（多半是参数和优化器状态放不下，需要切分或量化），还是跑了一阵才OOM（多半是某些长序列让激活暴涨，或碎片积累）。PyTorch提供显存快照工具，可以看到每块显存是谁分配的。

例子

一个1B参数模型，混合精度+Adam：参数、梯度、优化器状态共约16GB。设24层、隐藏维度2048、序列长度2048、微批8条，粗略按每层每token保存约30个隐藏维度大小的BF16张量估算，激活约为24 × 8 × 2048 × 2048 × 30 × 2字节 ≈ 48GB，是参数部分的3倍。开启逐层梯度检查点后，只存每层输入，激活降到约24 × 8 × 2048 × 2048 × 2字节 ≈ 1.6GB（外加反向时单层重算的峰值）。系数30为示意。

容易误解的地方

  • 只把批大小减半不一定能解决OOM：若瓶颈是参数和优化器状态，激活再小也放不下。
  • 显存监控里显示的“已保留”与“已分配”不同，分配器会缓存释放的显存以便复用，看起来占满不等于真的用满。
