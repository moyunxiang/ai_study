正则表达式

Regular Expressions

也叫：regular expression　regex　regexp　正则表达式　正则　模式匹配　pattern matching　有限状态自动机　finite-state automaton　FSA　正则语言　regular language

在交互版中打开（看它长在树上的哪里）

一种描述字符串模式的小语言，如\d{3}-\d{4}匹配“三位数字-四位数字”。它是文本处理最基本的工具，用于抽取、清洗、分词规则，也是大模型约束解码的一种约束形式。

先要会：图、树与搜索

找出一份文档里所有的邮箱地址、把所有日期统一成同一格式、把文本按空格和标点切开——这些任务都需要描述“什么样的字符串算一个匹配”。逐个字符写判断很繁琐，正则表达式（regular expression，regex）提供了一套紧凑的写法。编辑距离与它一起，是Jurafsky与Martin教材开篇讲的文本处理基础。

基本语法（各语言的实现大同小异）。

  • 字符类：[abc]匹配a、b、c之一；[0-9]或\d匹配数字；\w匹配字母数字下划线；.匹配任意字符。
  • 数量：*零次或多次，+一次或多次，?零次或一次，{m,n}m到n次。
  • 位置：^行首，$行尾，\b词边界。
  • 选择与分组：a|b二选一，( … )分组并捕获匹配内容。

例如[\w.]+@[\w-]+\.[a-z]+能匹配大多数简单的邮箱地址。

理论背景。正则表达式与有限状态自动机等价：任何正则表达式都能编译成一个有限自动机，逐字符地在状态间转移，扫描一遍文本就能判断是否匹配。在乔姆斯基层级中，它描述的“正则语言”是能力最弱的一级，无法表达任意深度的括号嵌套，这类结构需要上下文无关文法。（很多编程语言的正则引擎加入了反向引用等扩展，已经超出了严格意义上的正则语言，代价是某些模式下匹配时间可能指数爆炸。）

在NLP和AI里出现在哪里。

  • 早期对话系统ELIZA本质上就是一组模式匹配与替换规则。
  • 分词：GPT-2系列的分词器先用一条正则把文本预切分成单词、数字、标点块，再在块内做BPE（见分词与token）。
  • 数据清洗：预训练语料处理中大量规则过滤都用正则实现（见预训练语料的清洗、过滤与去重、文本规范化与分句）。
  • 评测：从模型输出里用正则抽取最终答案（如“答案是(\d+)”），再与标准答案比较（见精确匹配与token级F1）。
  • 约束解码：把正则编译成自动机，生成时每一步只允许能让输出继续匹配的token，保证输出一定符合格式（见结构化生成与约束解码、约束解码Outlines）。

例子

从文本“请在2026-11-27或2026-12-01之前回复”中抽取日期，正则(\d{4})-(\d{2})-(\d{2})：

  • 第一次匹配“2026-11-27”，三个分组分别是2026、11、27。
  • 第二次匹配“2026-12-01”。

替换为“\2/\3/\1”后，文本变成“请在11/27/2026或12/01/2026之前回复”。

一个常见陷阱：贪婪匹配。对“<b>粗</b>和<b>体</b>”用<b>.*</b>会一次匹配整串；改成非贪婪的<b>.*?</b>才会分别匹配两个。

容易误解的地方

  • 正则擅长格式明确的模式，不适合处理嵌套结构（HTML、JSON）或需要语义理解的任务。
  • 用正则从模型输出里抽答案，格式稍有变化就会抽错，评测结果可能因此偏低，要检查抽取失败的样本。
