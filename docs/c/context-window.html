上下文窗口

Context Window

也叫：上下文长度　context length　长上下文　long context　最大token数　上下文窗口长度

在交互版中打开（看它长在树上的哪里）

语言模型一次能看到的最大token数，包括输入的提示和它已经生成的内容。超出窗口的内容，模型完全看不到。

先要会：分词与token 语言模型

语言模型没有“读过就记住”的能力。它在生成每个token时，能参考的只有当前输入里的那一段token序列——这一段的最大长度就是上下文窗口。窗口里的内容可以是系统提示、对话历史、粘贴进来的文档、工具返回的结果，以及模型自己刚写的回答。窗口外的东西，对模型来说等于不存在。所以“和大模型聊天时它记得前面说过的话”，其实是每一轮都把整个对话历史重新放进了窗口。

长度按token计算（见分词与token），不是按字数。

为什么窗口有限。三个原因叠加：

  • 计算量：标准自注意力与多头注意力要计算每对token之间的分数，长度为n时有n²对。长度翻10倍，注意力的计算量翻100倍。
  • 显存：生成时要为窗口内每个token缓存键和值（见KV缓存），显存与长度成正比，长上下文时常比模型权重本身还大。
  • 位置编码的外推：模型只在训练时见过的长度内学会了如何使用位置信息（见位置编码），直接用于更长的输入往往失效。

窗口是怎么变长的。BERT是512个token，GPT-2是1024，GPT-3是2048。Transformer-XL让模型能借用上一段的隐状态；Longformer滑窗注意力等稀疏注意力只计算部分token对；FlashAttention降低了精确注意力的显存开销；位置插值扩上下文和YaRN通过调整RoPE的角度，用少量训练把窗口扩大数倍。2023年Claude 2与100K上下文提供10万token的窗口，2024年Gemini 1.5与百万上下文达到100万token。

窗口大不等于用得好。迷失在中间发现，相关信息放在长输入的开头或结尾时模型答得好，放在中间时明显变差。长上下文是否真正被利用，需要专门的评测来检验。

例子

一次对话怎么占窗口。假设窗口是8,000个token：系统提示500个，之前10轮对话共5,000个，用户这次粘贴了一份2,000个token的文档并提问（100个token）。已用7,600个，模型的回答最多只剩400个token的空间。再聊下去，应用程序必须删掉或总结最早的对话，否则放不下——被删掉的部分模型就“忘了”。

平方增长。长度1,000时注意力分数矩阵有10^6个元素；长度100,000时有10^10个元素，是前者的1万倍，而长度只增加了100倍。

容易误解的地方

  • 上下文窗口不是记忆：每次请求结束后什么也没留下，模型的参数不会因为对话而改变。
  • 宣称的窗口长度和有效长度是两回事：能放进去，不代表能在其中准确找到并综合信息。
  • 输出长度通常另有上限，往往比输入窗口小得多。
