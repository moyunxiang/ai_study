流式输出

Streaming Output

也叫：streaming　流式输出　流式生成　streaming output　token streaming　流式响应　SSE　server-sent events　打字机效果　stream=True　增量解码　incremental detokenization　TTFT　首token延迟　time to first token　TPOT　time per output token　ITL

在交互版中打开（看它长在树上的哪里）

模型每生成一小段token就立刻发给用户，而不是等整段回答写完再一次性返回。它不让生成变快，但让用户几乎马上看到开头，是聊天产品“打字机效果”的来源。

先要会：自回归生成 吞吐、延迟与批处理

自回归生成是一个token一个token串行产生的（见自回归生成），一段500个token的回答可能要十几秒才能写完。如果等全部生成完再返回，用户要盯着空白界面等十几秒；而第一个token其实在零点几秒后就已经出来了。流式输出利用了这一点：边生成边发送。

怎么实现。

  • 服务端：生成循环每产出一个或几个token，就把它们解码成文字，推送给客户端。HTTP接口常用SSE（Server-Sent Events，服务器推送事件）：一个长连接里连续发送一条条data: {...}消息，最后发送一个结束标记；也可以用WebSocket。
  • 客户端：收到一块就追加显示一块。

两个延迟指标。流式输出让用户关心的延迟拆成两部分（见吞吐、延迟与批处理和预填充与解码两阶段）：

  • 首token延迟（TTFT）：从发出请求到看到第一个字。主要取决于排队时间和预填充（处理整段提示）的时间。
  • 每token间隔（TPOT或ITL）：之后每个token之间的时间，决定文字“打出来”的速度。

总耗时没有变短，但用户感知的等待从“总时间”降到了“首token延迟”。

几个实现上的坑。

  • 多字节字符被切开。字节级分词器（见分词与token）可能把一个汉字的3个UTF-8字节分到两个token里，单独解码第一个token会得到乱码。增量解码要缓存不完整的字节，等凑齐再输出。
  • 停止序列跨token。见生成的停止条件：可能构成停止序列前缀的文字要先缓存，确认不是停止序列后再发送。
  • 结构化输出与工具调用。JSON或函数参数在流式过程中是不完整的，客户端要么等完整后再解析，要么用能处理半截JSON的增量解析器（见工具调用）。
  • 审核。内容安全检查如果要看完整回答才能判断，就与流式输出冲突，常见折中是对已生成部分分段检查。

流式输出在ChatGPT发布等对话产品中是默认体验，推理框架如vLLM与PagedAttention和主流API都提供流式接口。

例子

一段回答共400个token。预填充用时0.4秒，之后每个token约0.03秒：

  • 非流式：用户等 0.4 + 400×0.03 = 12.4秒后，一次看到全文。
  • 流式：0.4秒后看到第一个字，之后每秒约33个token的速度往外冒，12.4秒时显示完毕。

多字节问题：“好”的UTF-8编码是3个字节E5 A5 BD。若分词器把它拆成两个token（E5 A5 | BD），收到第一个token时解码得到无效字节，应暂不显示，等第二个token到达后再输出“好”。

容易误解的地方

  • 流式输出改善的是感知延迟，不是吞吐；服务端为维持大量长连接也要付出额外开销。
  • 流式过程中用户看到的半截内容可能在后面被模型自己“推翻”，不能把中途内容当作最终结果使用。
