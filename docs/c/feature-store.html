特征存储与训练—服务一致性

Feature Stores and Training–Serving Consistency

也叫：特征存储　特征仓库　特征平台　feature store　feature platform　训练服务偏差　训练-服务偏差　training-serving skew　时间点正确　point-in-time correctness　point-in-time join　时间穿越　在线特征　online features　离线特征　offline features　Feast　Tecton　特征管理

集中管理特征的基础设施：同一份特征定义既能批量算出历史值供训练，也能低延迟提供最新值供推理，保证训练和服务用同一套特征，避免训练—服务偏差和时间穿越泄漏。

先要会：特征与表示学习 训练集、验证集与测试集

推荐、风控、广告这类系统的模型往往依赖成百上千个特征：用户最近7天的点击次数、商品过去一小时的销量、账户注册天数……这些特征散落在不同的数据表和流水线里，由不同团队各自计算。问题随之而来：

  • 训练—服务偏差：离线训练时用SQL批量算出的“最近7天点击数”，与线上服务时用另一段代码实时算出的值，口径稍有不同，模型上线后效果就莫名变差。
  • 时间穿越：构造训练样本时，不小心用了事件发生之后才产生的数据（比如用“今天的累计销量”去预测“今天上午的点击”），离线指标虚高（见数据泄漏与基准污染和数据划分：分层、分组与按时间划分）。
  • 重复建设：不同模型各自重算同一个特征，浪费算力，结果还不一致。

特征存储把特征当作一等公民来管理：

  • 统一定义：特征的计算逻辑只写一次，登记名称、类型、负责人和更新频率。
  • 离线存储：保存特征的完整历史（通常在数据仓库或数据湖中），用于生成训练集。关键操作是按时间点正确的连接：为每条训练样本只取它发生那一刻之前已经可得的特征值。
  • 在线存储：用低延迟的键值数据库保存每个实体（用户、商品）的最新特征值，推理时毫秒级读取。
  • 物化与同步：批处理或流处理任务定期把特征计算出来，同时写入离线和在线两边，保证一致。
  • 监控与发现：监控特征分布是否漂移（见分布偏移），让其他团队能检索和复用已有特征。

开源的Feast、商业化的Tecton，以及Uber的Michelangelo等内部平台是常见例子。它是MLOps体系中与模型注册表、实验追踪（实验追踪：W&B与MLflow）并列的组件；机器学习系统的技术债所说的机器学习系统技术债，很大一部分正来自特征与数据管道，TFX生产机器学习平台等平台也把特征的一致性作为核心设计目标。

与深度学习、大模型的关系。端到端的深度模型减少了手工特征工程（见特征与表示学习），但推荐、风控等工业系统仍大量依赖实时统计特征（见推荐系统与协同过滤）；大模型应用中，检索用的检索与向量数据库向量索引和用户画像也面临类似的“离线构建、在线服务、保持一致”问题。

例子

风控模型的特征“用户过去24小时交易次数”。训练样本是2026-03-01 10:00的一笔交易，按时间点正确的连接只统计2026-02-28 10:00到2026-03-01 10:00之间的交易（比如3次），而不是当天全天的统计（比如11次，包含了这笔交易之后发生的8次）。线上推理时，在线存储里实时维护同一个滑动窗口计数，读出的值与训练时的口径完全一致。

容易误解的地方

  • 特征存储解决的是一致性和复用，不会自动保证特征有用；没人维护的特征越积越多，反而成为负担。
  • 实时特征的更新延迟（流处理落后几秒到几分钟）也要在训练时模拟，否则仍会出现细微的训练—服务偏差。
