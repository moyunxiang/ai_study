工具调用

Tool Calling

也叫：function calling　函数调用　工具使用　tool use　插件　API调用　MCP

在交互版中打开（看它长在树上的哪里）

让语言模型在回答过程中输出一段结构化的“调用请求”（调用哪个函数、传什么参数），由外部程序真正执行，再把结果放回上下文供模型继续。模型由此能查资料、算数、操作软件。

先要会：指令微调与对话模板 上下文窗口 自回归生成

语言模型只会生成文本，有几件事它天生做不好：知道今天的日期和最新新闻（知识截止于训练时）、精确计算大数乘法、查询私有数据库、真正去发邮件或改文件。但这些都是普通程序很擅长的。工具调用把两者接起来：模型负责判断“什么时候需要什么工具、参数是什么”，程序负责执行。

一次调用的完整流程。

1. 声明工具。开发者在请求里描述可用的工具：名称、用途说明、参数的JSON Schema（参数名、类型、是否必填）。这些描述被放进模型的上下文（见上下文窗口）。 2. 模型决定调用。模型读完用户的问题，如果判断需要工具，就生成一段特殊格式的输出（通常是JSON），写明工具名和参数，然后停下来，不再继续写回答。 3. 程序执行。应用程序解析这段输出，真正去调用函数或API，拿到结果。 4. 结果回传。把工具的返回值按对话模板作为一条新消息放回上下文（见指令微调与对话模板）。 5. 模型继续。模型读到结果后，要么写出最终回答，要么再调用下一个工具。

模型本身从不直接执行任何东西，它只是生成文本；“调用”是应用程序根据这段文本完成的。

模型怎么学会的。Toolformer让模型自己在文本中插入API调用，保留那些能降低后续预测损失的调用作为训练数据；WebGPT训练模型使用文本浏览器搜索网页。2023年OpenAI等把它做成了API的标准功能（函数调用成为标准接口）：模型经过专门微调，按开发者给的Schema输出参数。2024年的模型上下文协议MCP进一步统一了“工具如何向模型描述自己”的协议，让同一个工具可以接入不同的应用。

它在哪里出现。检索（见检索与向量数据库）、代码执行、计算器都是常见工具。把“思考—调用工具—看结果—再思考”反复进行，就是智能体（见智能体循环），ReAct是这种模式的早期代表。

例子

查询天气。开发者声明了一个工具get_weather，参数是city（字符串，必填）。

1. 用户：“北京今天要带伞吗？” 2. 模型输出（不是给用户看的）：{'name': 'get_weather', 'arguments': {'city': '北京'}}（实际是标准JSON，这里为排版用单引号） 3. 程序调用天气API，得到“小雨，18°C”，作为工具结果放回上下文。 4. 模型读到结果后回答：“北京今天有小雨，建议带伞。”

这一轮对话中模型被调用了两次：第一次生成调用请求，第二次根据结果写回答。上下文里依次是：工具声明、用户问题、调用请求、工具结果、最终回答。

容易误解的地方

  • 模型可能生成不存在的工具名或格式错误的参数，程序必须校验，不能盲目执行。
  • 工具返回的内容会进入模型上下文，如果其中含有恶意指令（如网页里藏着“忽略之前的要求”），可能劫持模型行为，这叫提示注入。
  • 有副作用的工具（删除文件、付款、发消息）应当要求人工确认，不能完全交给模型决定。
