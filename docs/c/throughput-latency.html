吞吐、延迟与批处理

Throughput, Latency and Batching

也叫：吞吐量　TTFT　首字延迟

在交互版中打开（看它长在树上的哪里）

延迟是一个请求从发出到得到结果要等多久，吞吐是系统每秒总共能处理多少；把多个请求拼成一批一起算能大幅提高吞吐，但通常会让单个请求等得更久。

先要会：显存、内存带宽与“内存墙”

同一块GPU服务大模型，可以让一个用户感觉“秒回”，也可以同时服务几百个用户但每人都慢一点。这两个目标冲突，部署推理服务的核心工作就是在两者之间取舍。

两个指标。延迟（latency）：单个请求的耗时，单位毫秒或秒。吞吐（throughput）：单位时间完成的工作量，例如每秒处理的token数或图片数。对语言模型，延迟又分两段：首token延迟（TTFT），即读完整个提示并输出第一个token要多久；每token延迟（TPOT），即之后每生成一个token要多久，决定文字“流出来”的速度。

为什么批处理能提高吞吐。逐token生成时，GPU每一步都要把全部权重从显存读一遍，计算本身很少，瓶颈在带宽（见显存、内存带宽与“内存墙”）。如果把32个用户的请求放进同一批，权重仍只读一遍，却同时为32个人各算出一个token——读数据的成本被32人分摊，吞吐几乎提高32倍，而每一步耗时几乎不变。批再变大，计算量最终追上读数据的时间，系统从带宽受限变成算力受限，每一步开始变慢，单个用户感到延迟上升。

两个阶段性质不同。处理提示的预填充（prefill）一次并行处理几千个token，本身就是算力受限；逐个生成的解码（decode）是带宽受限。两者混在一起会互相拖慢，所以出现了分块预填充Sarathi的分块预填充和预填充-解码分离部署的预填充-解码分离部署。

它出现在哪里：Orca连续批处理提出连续批处理（每一步都可以有请求加入或退出批，不必等整批结束），vLLM与PagedAttention用分页管理KV缓存让批能做得更大，推测解码则用小模型先猜几个token、大模型一次验证，以减少解码步数，从而降低延迟。训练也有同样的取舍，见批大小、步数与轮数和训练与推理的算力差别。

例子

仍以7B模型FP16（14GB权重）在H100（带宽3.35TB/s，BF16约989 TFLOPS）上逐token生成为例，只看理想上限、忽略KV缓存：读一遍权重约4.18毫秒，每个token的计算约0.014毫秒。

  • 批大小1：每步4.18毫秒，吞吐约240 token/s。
  • 批大小32：计算0.45毫秒，仍小于读权重的时间，每步还是约4.18毫秒，吞吐约7,700 token/s，提高32倍，每个用户的速度几乎不变。
  • 批大小512：计算约7.25毫秒，超过读权重的时间，每步变成7.25毫秒，总吞吐约70,600 token/s，但每个用户的生成速度降了约42%。

容易误解的地方

  • 吞吐高不等于用户体验好：离线批量任务（打标签、合成数据）追求吞吐，聊天和机器人控制更看重延迟。
  • 实际系统里KV缓存会随批大小和上下文长度线性增长，常常先于算力成为批大小的上限。
  • 平均延迟会掩盖长尾，服务指标通常看P50、P99等分位数。
