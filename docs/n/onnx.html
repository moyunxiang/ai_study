ONNX模型交换格式

2017.09系统延伸Facebook · Microsoft待核对
ONNX（维基） ↗在交互版中打开（演化树、学习进度）

问题

模型在PyTorch里训练，却要部署到别的运行时或硬件上；每个框架有自己的格式，互相转换要一对一写适配。

方法

定义一个开放的模型交换格式：把网络表示为算子组成的计算图，用Protocol Buffers存储，各框架导出、各运行时导入。

影响

成为跨框架、跨硬件部署的通用中间格式，PyTorch模型导出后可在多种运行时和加速器上推理。

方法

ONNX最初叫Toffee，由Facebook的PyTorch团队开发，2017年9月与Microsoft共同公布并更名。它把模型表示为由标准算子构成的计算图，容器格式是Protocol Buffers，重点是推理而非训练。

这样N个框架与M个运行时之间的适配从N×M降为N+M：框架只需实现导出器，运行时或硬件厂商只需实现导入器。维基记载IBM、华为、Intel、AMD、Arm、Qualcomm后来宣布支持，2019年11月ONNX成为Linux Foundation AI的毕业项目。

局限与后续

  • 动态控制流、自定义算子难以表示，导出时常需绕开。
    后来针对它的工作　PyTorch 1.0与TorchScript
  • 格式固定在算子集上，新算子出现后跟进有滞后。
    本站还没有记录针对它的后续工作（不代表没有人解决）

它建立在什么之上

  • 延续
    PyTorch2017.01 · 系统·效率 待核对
    给动态图的PyTorch一条通往生产部署的导出路径。
  • 竞争
    TensorFlow2015.11 · 系统·效率
    TensorFlow自有SavedModel格式，ONNX试图成为中立标准。
  • 竞争
    Caffe2013.12 · 系统·效率
    同样想统一部署表示，Caffe模型格式只覆盖自家框架。
  • 改进
    Chainer与Define-by-Run2015.06 · 系统·效率
    模型就是Python代码，部署到没有Python的移动端或服务器C++环境很困难。
  • 改进
    Caffe Model Zoo2014 · 系统·效率
    不同框架权重格式互不通用，模型从一个框架迁到另一个要手工转换。
  • 改进
    TensorRT2016 · 系统·效率
    只面向NVIDIA GPU，引擎文件绑定特定GPU型号和版本，不可移植。
  • 改进
    微软CNTK开源2016.01 · 系统·效率
    生态与模型库不及主流框架，后来微软转向PyTorch和ONNX。
  • 改进
    Core ML2017.06 · 系统·效率
    早期只支持推理，且依赖转换工具，新算子支持滞后。
  • 改进
    TensorFlow Lite2017.11 · 系统·效率
    转换器支持的算子少于完整TensorFlow，复杂模型需改写。

后来的相关工作

  • 使用
    Hugging Face Transformers2018.11 · 系统·效率
    模型可导出为ONNX格式部署，论文报告与ONNX团队合作后推理加速接近4倍。
  • 使用
    PyTorch 1.0与TorchScript2018.12 · 系统·效率
    脚本和追踪的结果可以导出为ONNX。
  • 使用
    MNN移动端推理引擎2020.02 · 系统·效率
    支持从ONNX等多种训练框架格式转换模型，解决模型兼容性问题。
