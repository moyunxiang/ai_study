PyTorch 2与torch.compile

PyTorch 2: Faster Machine Learning Through Dynamic Python Bytecode Transformation and Graph Compilation
2023.03系统重要ASPLOS 2024（PyTorch 2.0发布于2023-03）Jason Ansel, Edward Z. Yang, Horace He, Natalia Gimelshein, Animesh Jain, Michael Voznesensky, Bin Bao, Peter Bell et al. · Meta / PyTorch团队待核对
论文（ACM） ↗PyTorch 2.0发布博客 ↗论文PDF ↗在交互版中打开（演化树、学习进度）

问题

PyTorch的即时执行（eager）好写好调，但框架一次只看到一个算子，无法做算子融合等全图优化；此前的图捕获工具TorchScript在真实模型上只有约一半能用。

方法

在Python解释器执行字节码之前拦截它，把其中连续的PyTorch操作抽成计算图交给编译器，遇到看不懂的Python代码就“断图”回退执行，用户只需加一行torch.compile。

影响

让PyTorch在保留eager体验的同时获得编译器加速：默认后端把模型编译成Triton内核，在180多个真实模型上推理几何平均提速2.27倍，成为今天训练和推理大模型的常规手段。

背景

PyTorch胜出的原因是即时执行：每行Python代码立刻在GPU上算出结果，可以随意打印、用if和循环、单步调试。代价是框架每次只看到一个算子，比如x * w + b后接GELU会变成三四个独立的GPU内核，每个都要把中间结果写回显存再读出来，很多时间花在搬数据上（见显存、内存带宽与“内存墙”）。TensorFlow、JAX借助XLA编译器能整图编译，但要求用户按图的方式写程序。

PyTorch此前尝试过几种图捕获：PyTorch 1.0与TorchScript的TorchScript要么记录一次运行轨迹（遇到数据相关的分支就会错），要么解析Python源码（只支持Python的一个子集）。论文统计，torch.jit.script在TorchBench真实模型上只有约一半能成功，Hugging Face的模型因为返回特殊的输出类型全部失败；用户常要花几周改写代码才能“TorchScript化”一个大模型。

方法

TorchDynamo：在字节码层面捕获图。CPython的PEP 523允许替换函数帧的求值函数。TorchDynamo在每个Python函数执行前分析它的字节码，把其中的PyTorch张量操作记录成一个FX图；遇到无法处理的东西（打印、调用C扩展、依赖张量具体数值的分支）就在那里断图：前半段图交给编译器，那段Python照常执行，之后再继续捕获。编译结果会被缓存，并附带守卫（guard）：检查张量形状、类型、全局状态等假设是否仍成立，成立就直接复用，否则重新编译。因此用户代码无需任何改动。

AOTAutograd：在编译前把反向传播图也提前生成出来，使训练时的前向和反向都能被编译。

TorchInductor：默认后端。把FX图降低成一套循环级的中间表示，做算子融合、内存规划等优化，然后在GPU上生成Triton GPU编程语言内核、在CPU上生成C++代码。例如逐元素操作和归约可以融合成一个Triton内核，中间结果留在片上不落显存。

结果

图捕获：在TorchBench的80个模型上，TorchDynamo成功74个（93%），TorchScript只有36个（45%）。加速：在NVIDIA A100上的180多个真实模型（TorchBench、Hugging Face、TIMM）中，TorchInductor推理几何平均提速2.27倍、训练1.41倍，优于论文比较的另外六种编译后端。PyTorch 2.0于2023年3月15日发布，torch.compile是其主要新接口，并且完全向后兼容。

后来的发展

torch.compile成为PyTorch训练和推理的常规选项：TorchTitan等大规模训练框架把它与PyTorch FSDP组合使用，vLLM与PagedAttention、SGLang与RadixAttention等推理引擎用它融合非注意力部分的算子；ExecuTorch 1.0借助同一套图捕获把模型导出到手机和边缘设备。它也让Triton GPU编程语言从少数专家的工具变成了框架默认的代码生成目标。

容易误解的地方

  • torch.compile不是把整个程序变成静态图：断图越多，能融合的部分越少，加速越小。
  • 第一次运行要编译，可能需要几十秒到几分钟；张量形状频繁变化会触发反复重编译。
  • 它主要省的是显存读写和Python开销，对已经被大矩阵乘主导的模型，加速有限。

局限与后续

  • 动态形状、数据相关的控制流会导致断图和反复重编译，首次编译时间长，在线服务里难以预测延迟。

读懂它需要的概念

自动微分与计算图 CPU、GPU与并行计算 显存、内存带宽与“内存墙” 反向传播

本篇术语

  • 即时执行（eager mode）　每条运算语句立刻执行并得到结果，与先构建完整计算图再统一执行的“图模式”相对。
  • 断图（graph break）　TorchDynamo遇到无法放进图里的Python代码时，把图在此处切开，前后各自编译，中间那段照常由Python执行。
  • 守卫（guard）　编译时所做假设（如张量形状、数据类型）的检查函数；下次调用时假设成立就复用编译结果，否则重新编译。
  • 算子融合　把多个原本各自读写显存的算子合并成一个GPU内核，中间结果留在片上，减少显存读写。

怎么学

先确认会自动微分与计算图，理解PyTorch即时执行的方式。然后读论文第2节（以往图捕获方法的问题）和第3节（TorchDynamo的守卫与断图）。动手：对一个小Transformer分别跑eager和torch.compile，比较速度；再设置环境变量TORCH_LOGS=graph_breaks,output_code，查看断图位置和生成的Triton代码。
