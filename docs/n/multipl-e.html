MultiPL-E多语言代码

MultiPL-E: A Scalable and Extensible Approach to Benchmarking Neural Code Generation
2022.08数据集延伸IEEE Transactions on Software Engineering 2023Federico Cassano, John Gouwar, Daniel Nguyen, Sydney Nguyen, Luna Phipps-Costin, Donald Pinckney, Ming-Ho Yee, Yangtian Zi et al. · 美国东北大学（Northeastern）等待核对
arXiv ↗在交互版中打开（演化树、学习进度）

问题

代码模型训练时见过很多种语言，但评测几乎只用Python的HumanEval和MBPP，没人知道它们在Lua、Racket、Julia上写得怎么样。

方法

不翻译解答，只写一批“小编译器”把Python题目的函数签名、单元测试、文档注释和类型标注翻成其他语言，一次把HumanEval和MBPP扩成19种语言的平行基准。

影响

成为多语言代码生成的常用评测：StarCoder、Qwen2.5-Coder等代码模型的报告都用到它。

方法

关键观察是：执行式代码基准只需要题目和测试，解答由模型生成，所以不必翻译函数体。每种目标语言写一个约200行的小编译器，只翻四样东西：函数签名、简单单元测试中的常量与数据结构（列表、元组、字典等）、描述函数行为的注释与doctest、静态类型语言所需的类型标注；再配一个约20行的评测脚本负责运行和归类结果（通过、语法错误等）。

用这种方法把HumanEval的164题和MBPP扩展到另外18种语言，覆盖从JavaScript、C++到Bash、Perl、Lua、R、Julia、Swift、Racket等不同范式和流行度的语言，其中有8种以前从未用于评测自然语言生成代码，一半是静态类型语言。少数题无法翻译：有3道HumanEval题提示里含Python辅助函数被排除，某些类型语言里最多5题因类型无法表达而失败。

评测沿用Codex论文的pass@k：每题采样200个结果，用无偏估计计算。作者测了Codex、CodeGen、InCoder三个模型。

结果

Codex在JavaScript上表现很好，有时甚至超过Python；在C++、Scala、TypeScript上也不错。代码正确率与语言流行度相关，但困惑度与正确率没有强相关，作者据此认为困惑度不是代码能力的好指标。

后来的发展

StarCoder在选择训练语言时以MultiPL-E覆盖的语言为参照，Qwen2.5-Coder的技术报告把MultiPL-E列为衡量多语言代码生成的评测之一，并据此调整指令数据的配比。它说明了一种低成本扩展基准的办法：执行式评测只需翻译题目和测试，不必翻译解答。

局限与后续

  • 题目仍是HumanEval和MBPP那种短小的单函数练习，难度和题型继承了原基准，也继承了它们可能被训练数据污染的问题。
    本站还没有记录针对它的后续工作（不代表没有人解决）
  • 翻译出来的题目带着Python的思维方式，不能反映各语言自己的惯用写法和生态（库、构建工具）。

它建立在什么之上

  • 使用
    Codex2021.07 · LLM
    以Codex为主要被测模型，并沿用Codex论文的pass@k无偏估计方法。
  • 延续
    HumanEval2021.07 · 数据·评测
    把HumanEval的164道Python题翻成另外18种语言，形成MultiPL-HumanEval。
  • 延续
    MBPP2021.08 · 数据·评测
    同样把MBPP翻成18种语言，形成MultiPL-MBPP。
  • 使用
    CodeGen2022.03 · LLM
    CodeGen是三个被测的开源或闭源代码模型之一。

读懂它需要的概念

基准、排行榜与SOTA 语言模型 解码：贪心、束搜索、温度与top-p 分词与token

本篇术语

  • MultiPL-HumanEval / MultiPL-MBPP　MultiPL-E生成的两个平行基准：同一批题目在19种语言里各有一份，可以直接比较模型在不同语言上的通过率。
  • pass@k　每题采样多个程序，只要k个里有一个通过全部单元测试就算解出；通常用大量采样加无偏估计来计算。

怎么学

先读HumanEval理解执行式代码评测。读原文第3节（小编译器翻译哪些部分）和图6。动手：挑一道HumanEval题，自己把签名和测试手工翻成JavaScript和Lua，再让模型补全函数体并运行测试。
