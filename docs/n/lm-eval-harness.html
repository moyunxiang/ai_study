lm-eval可复现评测

Lessons from the Trenches on Reproducible Evaluation of Language Models
2024.05论文延伸Stella Biderman, Hailey Schoelkopf, Lintang Sutawika, Leo Gao, Jonathan Tow, Baber Abbasi, Alham Fikri Aji, Pawan Sasanka Ammanamanchi et al. · EleutherAI等待核对
arXiv ↗GitHub ↗在交互版中打开（演化树、学习进度）

问题

同一个模型在同一个基准上，换一种提示格式、答案打分方式或少样本示例，分数就能差好几个点；各家论文用各自的评测代码，数字既无法复现也无法互相比较。

方法

EleutherAI把维护了三年的开源评测库lm-eval（Language Model Evaluation Harness）的经验写成论文：归纳语言模型评测中的常见陷阱，给出最佳实践，并介绍lm-eval如何用统一的任务配置让“任何基准跑任何模型”。

影响

lm-eval是开源大模型最常用的评测后端之一，Hugging Face的Open LLM Leaderboard就建立在它上面；论文把大量“评测民间知识”写成了可引用的规范。

方法

背景。大模型论文里的基准数字通常来自各自实现的评测脚本。作者在研究中经常无法复现别人报告的结果。原因往往不在模型，而在细节：多选题是让模型生成答案字母，还是比较每个选项的对数似然；对数似然要不要按长度归一化；少样本示例选哪几条、用什么分隔符；输出怎么截断、怎么抽取答案。MMLU、BIG-bench这类基准都有过“同名不同分”的情况。HELM从覆盖面角度统一了评测，lm-eval则从工程角度把这些细节固定下来。

论文内容分三部分：

  • 常见挑战：模型对评测设置高度敏感；不同方法之间难以公平比较（例如不同的分词方式会影响对数似然）；缺乏可复现性和透明度；关于惯例的信息分散在各团队内部。
  • 最佳实践：公开完整的提示和评测代码；报告标准误而不只报一个点估计；比较模型时保证使用同一实现和同一设置；对任何改动做版本管理，任务定义一变就升版本号。
  • lm-eval本身：每个任务用一个配置文件描述数据来源、提示模板、打分方式和指标，同一份配置可以在本地Hugging Face模型、各种推理库和商业API上运行；论文给出了用它澄清方法学争议的案例。

意义。它属于“基准的可信度”这条线上偏工程的一环：问题不是考卷本身有错，而是同一张考卷的判卷方式不统一。

局限与后续

  • 统一了实现，并不能消除模型对提示格式的敏感性本身；对于需要多步交互、工具调用的智能体评测，基于单轮提示的框架覆盖有限。
    本站还没有记录针对它的后续工作（不代表没有人解决）

它建立在什么之上

  • 使用
    MMLU2020.09 · 数据·评测
    以MMLU等常用基准为例，说明提示格式和打分方式导致的分数差异。
  • 使用
    BIG-bench2022.06 · 数据·评测
    BIG-bench等大型任务集被收进lm-eval统一的任务配置中。
  • 竞争
    HELM2022.11 · 数据·评测
    HELM追求场景和指标的全面覆盖，lm-eval追求任意基准在任意模型上可复现地运行，两者常被并列作为评测框架。
  • 延续
    Open LLM Leaderboard2023 · 数据·评测
    Open LLM Leaderboard以lm-eval为评测后端，论文总结了这类大规模公开评测中暴露的可复现性问题。

读懂它需要的概念

基准、排行榜与SOTA 零样本与少样本 方差、种子与统计显著性 困惑度

本篇术语

  • 对数似然打分　多选题不让模型自由生成，而是算模型生成每个选项文本的概率，选概率最高的那个作为答案。
  • 长度归一化　选项越长，总概率越小，所以按字符或词数把对数似然平均一下再比较，结果会明显不同。

怎么学

先读MMLU了解多选基准；读这篇论文的第2节（挑战）和第3节（最佳实践）；动手用lm-eval对同一个小模型在一个多选任务上分别跑acc和acc_norm两种打分，再改少样本数，记录分数变化。
