Conductor指挥家模型

Learning to Orchestrate Agents in Natural Language with the Conductor
2025.12论文延伸Stefan Nielsen, Edoardo Cetin, Peter Schwendeman, Qi Sun, Jinglue Xu, Yujin Tang · Sakana AI / 密歇根大学 / 东京科学大学待核对
arXiv ↗在交互版中打开（演化树、学习进度）

问题

不同厂商的强模型各有所长，但怎样让它们分工协作——谁做哪一步、谁能看到谁的结果——一直靠人手工设计固定的流程。

方法

训练一个7B的指挥模型，用自然语言为每个问题写出协作方案：分几步、每步交给哪个模型、给它什么指令、它能看到之前哪些结果；只按最终答对与否做RL。

影响

7B指挥模型调度GPT-5、Gemini 2.5 Pro等工人模型，在多个推理基准上超过池中任何单个模型，被视为「协调策略可以纯靠RL学出来」的代表工作。

方法

指挥模型从Qwen2.5-7B初始化。面对一个问题，它先推理，然后输出三个并列的列表：每一步用哪个工人模型、给这个工人的自然语言子任务、这个工人能看到之前哪些步骤的回答（访问列表）。访问列表决定了智能体之间的通信拓扑，最多5步，训练后平均约3步。工人池有7个，包括GPT-5、Gemini 2.5 Pro、Claude Sonnet 4、Qwen3-32B等。

训练用GRPO、不加KL约束，只在960道数学、知识和编程题上跑200轮；奖励极简：输出无法解析得0，最终答案正确得1，否则0.5。训练时随机抽取不同的工人组合，所以指挥模型能适应任意给定的模型池。

不限制工人时，指挥模型在LiveCodeBench上83.93（最好的单个工人GPT-5为82.90），GPQA-Diamond上87.5（Gemini 2.5 Pro为84.8），七项平均77.27对74.78。如果允许指挥模型把自己也列为工人，就能递归地对自己的方案再规划一轮，形成一种新的测试时扩展。

局限与后续

  • 只学了最多5步、几个工人的短流程；智能体数量增多后的通信开销和协调问题没有处理。

  • 性能高度依赖调用昂贵的闭源工人模型，每道题的总花费远高于单次调用。

它建立在什么之上

  • 使用
    GRPO2024.02 · 推理·智能体
    用GRPO按最终答对与否训练指挥模型的协作方案。
  • 改进
    GPTSwarm智能体图优化2024.02 · 推理·智能体
    优化出的是每个任务一张固定的图，所有问题都用同一种协作结构，不会根据具体问题或中间状态临时调整。
  • 竞争
    混合智能体MoA2024.06 · 推理·智能体
    MoA用固定的分层结构，Conductor为每题学出拓扑和指令；在受限设置下四项平均72.35对MoA的62.13。
  • 竞争
    AFlow自动工作流2024.10 · 推理·智能体
    AFlow为整个任务离线搜索固定工作流，Conductor针对每个问题现场生成工作流。
  • 延续
    Puppeteer演化式编排2025.05 · 推理·智能体
    Puppeteer每步只选下一个智能体，Conductor一次写出包含子任务指令和可见范围的完整方案。

后来的相关工作

  • 改进
    OrchestraRL智能体群编排2026 · 推理·智能体
