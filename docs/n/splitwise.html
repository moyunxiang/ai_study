Splitwise阶段拆分推理

Splitwise: Efficient generative LLM inference using phase splitting
2023.11论文延伸ISCA 2024Pratyush Patel, Esha Choukse, Chaojie Zhang, Aashaka Shah, Íñigo Goiri, Saeed Maleki, Ricardo Bianchini · 华盛顿大学, 微软待核对
arXiv ↗在交互版中打开（演化树、学习进度）

问题

一次LLM请求分两段：处理提示词的预填充是计算密集的，逐个生成token的解码是访存密集的。两段挤在同一台机器上，解码阶段用不满最新GPU的算力，却同样花着最贵的硬件和电力。

方法

把一次请求的两个阶段放到不同的机器池上：预填充池用算力强的GPU，解码池可以用更便宜、更省电的GPU；预填充算完的KV缓存通过集群里的高速互连传给解码机器。

影响

与DistServe同期，确立了“预填充—解码分离”这一推理集群设计，它随后成为Mooncake、NVIDIA Dynamo、llm-d等大规模推理系统的标准做法。

方法

作者基于微软生产环境中的两类LLM服务做了大量测量，确认两个阶段的特性截然不同：预填充一次并行处理全部提示词token，算力利用率高，对应首token延迟；解码每步只生成一个token，要把权重和KV缓存从显存读一遍，算力大量闲置（见KV缓存与显存、内存带宽与“内存墙”），对应逐token延迟。即便用了Orca连续批处理的连续批处理和vLLM与PagedAttention的显存管理，混在一起时仍会互相干扰，而且解码阶段并不需要最新GPU的全部算力，功耗也更低。

Splitwise据此把集群拆成提示池和token池，必要时还有一个可以动态改变角色的混合池。请求先在提示池完成预填充，再把生成的KV缓存通过GPU集群的高速后端互连（InfiniBand）逐层流式传到token池的机器，传输与计算重叠以隐藏延迟。两个池可以用同一种GPU，也可以用不同代的GPU（如H100做预填充、A100做解码），按吞吐、成本、功耗三个目标分别配置规模。

摘要报告：与当时的设计相比，可以在成本降低20%的情况下吞吐提高1.4倍；或在相同成本与功耗预算下吞吐提高2.35倍。

局限与后续

  • KV缓存要在机器之间传输，对互连带宽要求高；上下文很长时传输量很大，两池的比例也需要随负载动态调整。
