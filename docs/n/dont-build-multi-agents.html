《Don't Build Multi-Agents》

Don’t Build Multi-Agents
2025.06思想延伸Walden Yan · Cognition待核对
Cognition博客 ↗在交互版中打开（演化树、学习进度）

问题

AutoGen、OpenAI Swarm等框架推广「拆成多个子智能体并行干活再合并」的架构；在需要长时间稳定运行的生产系统里，这种做法为什么经常出问题？

方法

提出两条原则：共享完整上下文（整条智能体轨迹，而不只是单条消息）；每个动作都隐含决策，互相冲突的决策会带来坏结果。据此建议默认用单线程线性智能体，上下文太长时再加一个专门压缩历史的模型。

影响

发表于2025年6月12日，与次日Anthropic介绍其多智能体研究系统的文章几乎同时，形成「单智能体还是多智能体」的公开争论；也是较早系统讲「上下文工程」的文章之一。

方法

作者是编码智能体Devin背后的Cognition公司的工程师。文章用一个例子说明多智能体的脆弱：任务是「做一个Flappy Bird复刻」，主智能体拆成「做背景和管道」「做小鸟」两个子任务交给两个子智能体。结果一个做出了超级马里奥风格的背景，另一个做的小鸟既不像游戏素材、动作也不对，最后合并的智能体只能收拾两份误解。

  • 即使把原始任务一起传给子智能体，真实系统里还有多轮对话和工具调用中形成的大量细节，于是有原则1：共享上下文，并且共享完整的智能体轨迹。
  • 即使都看到原始任务，两个子智能体互相看不到对方在做什么，画风仍可能完全不一致，于是有原则2：行动隐含决策，冲突的决策带来坏结果。

最简单的满足方式是单线程、上下文连续的线性智能体；任务长到上下文装不下时，可以引入一个专门把历史压缩成关键细节、事件和决策的模型（文中说Cognition为此微调过较小的模型）。文章还举例：截至2025年6月，Claude Code与终端编码智能体的子智能体从不和主智能体并行写代码，通常只负责回答一个定义清楚的问题，好处是调查过程不必留在主智能体的上下文里。

局限与后续
