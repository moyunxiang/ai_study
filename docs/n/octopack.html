OctoPack与CommitPack

OctoPack: Instruction Tuning Code Large Language Models
2023.08论文延伸ICLR 2024Niklas Muennighoff, Qian Liu, Armel Zebaze, Qinkai Zheng, Binyuan Hui, Terry Yue Zhuo, Swayam Singh, Xiangru Tang et al. · BigCode社区（Hugging Face等）待核对
arXiv ↗GitHub ↗在交互版中打开（演化树、学习进度）

问题

代码模型的指令微调数据大多是用GPT-4等闭源模型合成的，受许可限制、难以复现；评测也几乎只看Python代码生成，不考察修bug和解释代码。

方法

利用Git提交天然的“提交说明（指令）+代码改动（回答）”结构，整理出覆盖350种语言、4TB的提交数据CommitPack做指令微调，并把HumanEval扩展成6种语言、3类任务的HumanEvalPack。

影响

提供了不依赖闭源模型输出的代码指令数据来源，HumanEvalPack（尤其是代码修复HumanEvalFix）成为评测代码修改能力的常用基准之一。

方法

背景：WizardCoder用Evol-Instruct从闭源模型合成代码指令数据，效果好但数据来自OpenAI输出，许可受限；HumanEval只测Python的“根据文档字符串写函数”。

作者观察到，每个Git提交都有一条人写的提交说明（如“修复空列表时的越界错误”）和对应的代码改动，正好构成“指令-回答”对。他们从GitHub提交历史中整理出CommitPack：4TB、覆盖350种编程语言；再筛选出质量较高的子集CommitPackFT用于微调。在16B参数的StarCoder上，他们把CommitPack与其他自然语言和合成的代码指令数据（xP3x、Self-Instruct、OASST）对比。

评测上提出HumanEvalPack：把HumanEval的164道题翻译到Python、JavaScript、Java、Go、C++、Rust六种语言，并扩展出三类任务——代码修复（给出有bug的代码和失败的测试，要求修好）、代码解释（先用自然语言解释代码，再只根据解释重写代码）、代码合成。

摘要报告：在不使用OpenAI输出训练的模型中，HumanEval Python上取得最好成绩，pass@1为46.2%；OctoCoder（基于StarCoder）和OctoGeeX（基于CodeGeeX2）在HumanEvalPack上是许可宽松模型中表现最好的。

局限与后续

  • 提交说明往往简短、含糊，与用户实际提出的指令差别较大；OctoCoder的绝对水平仍明显落后于用GPT-4数据蒸馏的模型。

读懂它需要的概念

指令微调与对话模板 基准、排行榜与SOTA 预训练与微调 语言模型

本篇术语

  • pass@1　对每道题让模型生成一次代码，能通过全部单元测试的题目比例。
  • Git提交　版本控制中一次代码修改的记录，包含改动前后的代码差异和开发者写的提交说明。

怎么学

先读HumanEval和StarCoder；读本文CommitPack的过滤流程和HumanEvalPack三类任务的示例；动手：从一个开源仓库的提交历史里抽取“提交说明-代码改动”对，看哪些能当作好的指令数据。
