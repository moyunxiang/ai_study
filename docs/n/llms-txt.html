llms.txt网站约定

/llms.txt—a proposal to provide information to help LLMs use websites
2024.09思想延伸Jeremy Howard · Answer.AI待核对
Answer.AI博客 ↗提案页 ↗在交互版中打开（演化树、学习进度）

问题

网页是给人看的，正文裹在导航、广告和脚本里，转成干净文本既难又不准；整站内容又远超上下文窗口，编码助手和搜索型助手不知道该读哪些页面。

方法

建议网站在根目录放一个Markdown文件 /llms.txt：用固定格式写一段简介和一组精选链接，链接指向各页面的Markdown版本（在原URL后加 .md），让模型先读这份目录再按需取内容。

影响

提案页称两年后已有数千个网站发布llms.txt，文档平台会自动生成，OpenAI、Anthropic、Gemini的开发者文档也都提供；它成为智能体读取网站文档的一种事实惯例。

方法

2024年9月3日，Jeremy Howard在Answer.AI博客提出这个约定，定位是与robots.txt、sitemap并存：sitemap给搜索引擎列出全部页面，llms.txt给语言模型一份精选概览。

文件格式是受限的Markdown：一级标题写项目名（唯一必需的部分）；一段引用块写简短摘要；可选的说明段落；若干二级标题下列出形如 - [名称](URL): 说明 的链接列表，其中「Optional」一节放可以跳过的次要资料。这样的格式人和模型都能读，也能用普通的正则或解析器处理。配套建议是：有用的页面同时在「原URL + .md」处提供干净的Markdown版本。

它不规定上下文怎么拼装，只让网站作者把「最值得给模型读的内容」列出来，工具再据此生成上下文（例如把所有链接内容拼成一个完整文件）。提案页后来的第二版（作者称基于两年的采用经验修订）增加了用HTTP Link头和 rel=describedby 指向llms.txt、用 rel=alternate 指向Markdown版本等发现机制。它和模型上下文协议MCP一样属于「让模型更容易拿到外部信息」的约定，但只是一个静态文件，不需要服务端程序。

局限与后续

  • 只是自愿遵守的约定，没有标准化组织背书；网站提供的内容是否完整、是否与网页一致，模型无法验证。
    本站还没有记录针对它的后续工作（不代表没有人解决）
  • 主要面向文档类网站；需要登录、动态生成或交互操作的内容仍要靠浏览器智能体或专门的工具接口。
    本站还没有记录针对它的后续工作（不代表没有人解决）

它建立在什么之上

  • 延续
    检索增强生成RAG2020.05 · 推理·智能体
    把检索增强中「先找相关资料」这一步交给网站作者预先整理的目录。
  • 改进
    GitHub Copilot2021.06 · 推理·智能体
    编码助手常需读库文档，llms.txt给它们提供精简、可直接放进上下文的版本。
  • 延续
    迷失在中间2023.07 · LLM
    出发点之一是上下文有限、塞进整站内容效果和成本都差，应该只放精选内容。

这些关系由AI模型整理。“改进”指后来的工作针对它的某个问题做了改进，不代表问题已经解决；“竞争”指同一问题的不同路线，不代表谁取代了谁。标有“已核对”的对照过原始来源，其余未逐条核对。
