Quest查询感知KV稀疏

Quest: Query-Aware Sparsity for Efficient Long-Context LLM Inference
2024.06论文延伸ICML 2024Jiaming Tang, Yilong Zhao, Kan Zhu, Guangxuan Xiao, Baris Kasikci, Song Han · MIT, 上海交通大学, 华盛顿大学, NVIDIA待核对
arXiv ↗GitHub ↗在交互版中打开（演化树、学习进度）

问题

128K乃至1M上下文的模型解码时，每生成一个词都要读完整个KV缓存，速度随长度明显下降；H2O、StreamingLLM这类方法按固定规则永久丢掉一部分token，可一个token是否重要其实取决于当前的查询。

方法

不丢弃任何KV，而是按页记录每页内各维度Key的最小值和最大值；每步解码用当前Query估计每页可能的最大注意力分数，只把得分最高的K页读进来做注意力。

影响

确立了“查询感知、按页选择”的长上下文解码稀疏注意力做法，与分页KV缓存天然契合，被大量KV检索与稀疏解码工作作为基线，相关思路也进入了推理引擎的稀疏注意力实现。

方法

长上下文解码时，模型权重的读取量不变，而KV缓存随长度线性增长，注意力成了瓶颈。已有观察是：少量关键token主导了注意力结果。H2O KV缓存淘汰按累计注意力分数保留“重击者”，StreamingLLM与注意力汇聚保留开头的汇聚token和最近窗口，被淘汰的token就永久丢失；可论文发现，一个token是否关键高度依赖当前的Query，之前不重要的token，后面的问题可能恰好要用到。

Quest把KV缓存按vLLM与PagedAttention式的页（例如每页16个token）组织，为每一页存两个向量：这一页里所有Key在每个维度上的最小值m和最大值M。解码时，对当前查询q，逐维取 max(qᵢ·mᵢ, qᵢ·Mᵢ) 再求和，得到该页内任何Key与q的点积的上界，作为这一页的重要性估计。然后只加载得分最高的K页做精确注意力。所有KV仍保留在显存里，只是每步只读一小部分，所以对需要回看早先内容的任务也不会丢信息。

摘要报告：自注意力最多加速2.23倍，推理延迟最多降低7.03倍，在长依赖任务上精度损失可以忽略。

局限与后续

  • 所有KV仍要放在显存里，只省带宽不省容量；超长上下文下显存仍是上限，需要配合KV卸载或量化。
    后来针对它的工作　LMCache KV缓存层
  • 页级上界估计较粗，页内只有少数关键token时会多读不少无关内容；前几层等注意力分散的层效果差。

  • 改进
    H2O KV缓存淘汰2023.06 · 系统·效率
    H2O按历史分数永久淘汰token，Quest发现重要性依赖当前查询，改为保留全部KV、每步按查询选页。
  • 竞争
    StreamingLLM与注意力汇聚2023.09 · 系统·效率
    StreamingLLM只保留汇聚token与近期窗口，适合流式但会丢远处信息；Quest保留全部内容按需读取。
  • 延续
    Flash-Decoding长上下文解码2023.10 · 系统·效率
    同样针对长上下文解码时读取KV缓存的瓶颈，Quest进一步减少需要读取的KV量。
  • 改进
    PyramidKV分层KV压缩2024.06 · 系统·效率
