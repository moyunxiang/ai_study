Late Chunking后切块

Late Chunking: Contextual Chunk Embeddings Using Long-Context Embedding Models
2024.09论文延伸Michael Günther, Isabelle Mohr, Daniel James Williams, Bo Wang, Han Xiao · Jina AI / Weaviate待核对
arXiv ↗GitHub ↗在交互版中打开（演化树、学习进度）

问题

RAG要先把文档切成小块再分别编码，可切开后“它”“这座城市”这样的指代就丢了上下文：一块只写“人口超过385万”的文字，向量里根本看不出说的是柏林。

方法

把顺序反过来：先让长上下文嵌入模型一次读完整篇文档，得到每个词元带全文语境的向量，再按切块边界对这些词元向量分段做平均池化，得到每一块的向量。

影响

不需要额外训练、也不必调用LLM，就能让块向量带上全文语境；提出后很快被Jina等嵌入服务和向量数据库作为选项支持，常与Anthropic的“上下文检索”放在一起比较。

背景

向量检索通常在短文本上更准——一个向量能装的信息有限，长文档压成一个向量会“过度压缩”。所以检索增强生成RAG流水线习惯先切块再编码。另一方面，借助ALiBi线性偏置位置、旋转位置编码RoPE这类相对位置编码，嵌入模型的输入长度已经能到8192个词元（约十页文字），远大于一个段落。问题在于：先切再编码，块与块之间的信息就断开了。

方法

普通切块：文档 → 按句子或段落切成c₁、c₂… → 每块单独送进编码器 → 平均池化成一个向量。

后切块：文档整篇送进编码器 → 得到每个词元的向量 ϑ₁…ϑₘ，此时每个向量已通过自注意力看过全文 → 把原来的切块边界换算成词元位置 → 对每一段 [start, end] 求平均 e_i = Σϑ_j / (end − start + 1)。切块算法照旧，只是“切”这一步挪到了Transformer层的结构之后、池化之前，所以叫“late”。

例子（论文表1）：用jina-embeddings-v2-small，把柏林维基百科的三句话分别编码，和“Berlin”这个词比相似度。第二句“它有超过385万居民”普通切块为0.708，后切块为0.825；第三句“这座城市也是德国的一个州”从0.754升到0.850。

扩展：文档超过模型窗口时，用长后切块——切成若干带重叠的大段，每段内部再做后切块。还提出一种按片段池化（span pooling）的微调方法，进一步提高效果。

结果：在BeIR的若干小型检索任务上，多种模型、多种切块方式下后切块大多优于普通切块；作者也报告了块很大或文档本来就短时两者差不多的情形。

后来的发展

它和同月发布的上下文检索代表两条思路：后者让LLM给每块写一句上下文说明再编码，效果直观但要为每块调用一次LLM；后切块只改池化位置，几乎不增加成本。两者常被组合或对照使用。

局限与后续

  • 依赖长上下文嵌入模型，且必须对词元级向量做池化；只提供最终向量的闭源嵌入API用不了这个办法。

读懂它需要的概念

嵌入向量 检索与向量数据库 自注意力与多头注意力 上下文窗口 分词与token

本篇术语

  • 平均池化　把一串词元向量逐维求平均，得到一个固定长度的向量来代表整段文字。
  • 切块边界　切块算法给出的每块起止位置；后切块需要把字符位置换算成词元位置。

怎么学

先读Sentence-BERT理解池化 → 读原文第3节算法1和表1的柏林例子 → 动手：用一个开源长上下文嵌入模型，对同一篇文章分别做普通切块和后切块，比较代词所在块与实体名的余弦相似度。
