Orca连续批处理

Orca: A Distributed Serving System for Transformer-Based Generative Models
2022.07论文重要OSDI 2022Gyeong-In Yu, Joo Seong Jeong, Geon-Woo Kim, Soojeong Kim, Byung-Gon Chun · 首尔大学 / FriendliAI待核对

问题

生成式模型一个请求要迭代几十到上千步，而现有服务系统以“请求”为单位组批：先写完的请求要陪整批等到最后，新到的请求也得等整批结束才能进来。

方法

迭代级调度：每生成一个token就重新决定这一步批里有哪些请求，完成的立即返回、新来的立即加入；再用选择性批处理，让长短不一的请求能拼进同一批。

影响

提出了今天所说的“连续批处理”，此后vLLM、TensorRT-LLM、SGLang等几乎所有大模型推理引擎都采用这种调度方式。

背景

GPT-3这类模型是自回归生成的：一个请求先把提示一次性读进去，然后每次运行整个模型只产生一个新token，直到结束。当时的推理服务（NVIDIA Triton推理服务器配合FasterTransformer）沿用图像分类时代的做法：攒够一批请求，整批跑完再返回（见吞吐、延迟与批处理）。

对生成任务这很浪费。同一批里有的请求生成10个token就结束，有的要生成500个，前者必须陪后者空转；新到的请求只能排队等整批结束。批越大吞吐越高，但排队和陪跑带来的延迟也越大。

方法

迭代级调度。调度器不再把“一个请求”交给执行引擎，而是每次只让引擎在当前批上跑一次迭代（每个请求前进一个token）。每次迭代结束，调度器检查：哪些请求已生成结束符，立即返回给用户；有没有新请求到达，若显存允许就加入下一次迭代。批的成员每一步都在变化，这就是后来所说的连续批处理。

选择性批处理。难点是同一次迭代里的请求形状不一：有的正在读入3个token的提示，有的在逐个生成。Orca发现，线性层、LayerNorm、GeLU这些操作不关心token属于哪个请求，可以把所有请求的token摊平成一个[ΣL, H]的矩阵一起算；只有注意力需要区分请求，于是在注意力之前把批拆开、每个请求单独算，算完再合并回去。每个请求的K、V由一个KV管理器保存，供后续迭代使用（见KV缓存）。

分布式。百亿级以上的模型放不进一块GPU，Orca同时用层内切分（按Megatron-LM模型并行的方式切矩阵）和层间切分（按层分段做流水线，类似GPipe流水线并行），并让多个批在流水线的不同段上同时进行。

结果

在Azure上每台8块40GB A100的机器上测试，GPT-3 175B切分到16块GPU。在中位归一化延迟约190ms的水平下，FasterTransformer的吞吐是0.185请求/秒，Orca是6.81请求/秒，提升36.9倍。在13B、101B、175B、341B几种规模上，除101B模型低负载这一例外，Orca都同时取得更低的延迟和更高的吞吐。

后来的发展

迭代级调度很快成为默认做法。vLLM与PagedAttention在此之上解决了Orca留下的显存浪费问题；分块预填充Sarathi把长提示的预填充切块，与解码请求拼在同一迭代里；预填充-解码分离部署干脆把预填充和解码放到不同的GPU上。TensorRT-LLM把这种调度称为in-flight batching，SGLang与RadixAttention等引擎也都采用。

读懂它需要的概念

自回归生成 吞吐、延迟与批处理 KV缓存 分布式训练：数据并行与模型并行 Transformer层的结构

本篇术语

  • 连续批处理　批的成员每生成一步就可以变化：完成的请求离开，新请求补进来，GPU始终满载。Orca称之为迭代级调度。
  • 预填充与解码　预填充是一次性处理用户输入的全部提示token；解码是之后每次生成一个新token。前者计算密集，后者主要受显存带宽限制。
  • 选择性批处理　只对与请求无关的操作（线性层、归一化等）做批处理，注意力则按请求分开算，从而能把长度不同的请求放进同一批。

怎么学

先理解KV缓存和吞吐、延迟与批处理。然后读论文第3节（请求级调度的问题，图3、图4）和第4节的调度算法。动手：用一个小GPT-2写两个循环，一个整批生成到最长的请求结束，一个每步检查并替换已结束的请求，比较同样请求流下的吞吐。
