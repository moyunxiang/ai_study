PyTorch

PyTorch: An Imperative Style, High-Performance Deep Learning Library
2017.01系统主干2017年1月首次公开发布；论文 NeurIPS 2019Adam Paszke, Sam Gross, Francisco Massa, Adam Lerer, James Bradbury, Gregory Chanan, Trevor Killeen, Zeming Lin et al.（论文共21位；核心开发者含Soumith Chintala） · Facebook AI Research等来源已核对
arXiv（NeurIPS 2019论文） ↗官方教程：Learn the Basics ↗维基百科：PyTorch ↗在交互版中打开（演化树、学习进度）

问题

2016年的框架要么易用、要么快：TensorFlow、Theano的静态图快但难调试、难写动态模型；Chainer灵活但性能一般；Torch快但要写Lua，进不了Python生态。

方法

让深度学习程序就是普通Python程序：张量运算立即执行，自动微分在运行时记录计算再反向求导；性能靠C++核心、GPU异步执行、缓存显存分配器和引用计数等工程细节补回来。

影响

在研究界的使用比例快速上升（论文统计ICLR 2019有296篇投稿提到它），此后大量开源模型和代码库（如Hugging Face Transformers）以它为主要实现。

背景

到2016年，深度学习框架分成两派。静态图派（Theano与自动微分、TensorFlow）先构造计算图再执行，便于整体优化和部署，但程序里看不到真实数值，带分支、循环的模型要用专门的控制流算子，调试困难。命令式派中，Chainer与Define-by-Run首创define-by-run，代码就是Python，但性能不如静态图框架；Torch7有成熟高效的C/CUDA张量库，却要用Lua编写，与NumPy与SciPy、scikit-learn所在的Python科学计算生态隔绝。

同时，研究的模型越来越动态：变长序列的循环网络、树形网络、强化学习里的交互循环。论文开篇指出的矛盾是：已有框架在易用性和速度之间只能二选一。

方法

论文把设计原则概括为：研究者优先，宁可牺牲10%的速度换取简单得多的模型，但不能牺牲100%。

一切皆Python。层、模型、优化器、数据加载器都是普通的Python类。论文的例子：

class LinearLayer(Module): def forward(self, activations): t = torch.mm(activations, self.w) return t + self.b

前向就是一个方法，可以用if、for、递归，可以下断点打印任意中间张量；张量与NumPy数组可以通过torch.from_numpy()零拷贝互转。

运行时自动微分。采用运算符重载：每次执行一个可微运算，就在后台记录它的输入、输出和反向函数，形成一张只用于反向的图；loss.backward()时对它做反向模式自动微分（反向模式自动微分），然后optimizer.step()更新参数。这一方式来自Chainer与Define-by-Run、autograd：给NumPy求导的思路。用户可以继承torch.autograd.Function自定义前向和反向。

把性能做回来：

  • C++核心：张量、GPU与CPU算子、自动微分引擎都在C++库libtorch里实现，反向传播在多线程中执行、不占用Python全局解释器锁；卷积、矩阵乘法调用cuDNN和cuBLAS。
  • 控制流与数据流分离：Python只负责决定“下一个算哪个算子”，算子通过CUDA流异步排队到GPU上执行。CPU上解释Python的时间与GPU上的计算重叠，只要每个算子足够大，GPU就能被跑满。
  • 缓存显存分配器：cudaFree可能阻塞到所有GPU任务完成，于是PyTorch自己缓存已申请的显存并复用，分配尺寸向上取整到512字节以减少碎片。论文对ResNet-50的追踪显示，第一轮迭代因调用cudaMalloc/cudaFree明显变慢，之后分配器开始复用，开销消失。
  • 引用计数：张量一旦不再被引用立即释放显存，而不是等垃圾回收——论文特别提到Torch7依赖Lua的垃圾回收，用户常需手动触发回收。
  • 多进程：torch.multiprocessing把发往子进程的张量放入共享内存，方便实现多GPU数据并行和Hogwild!并行SGD式训练。

结果

论文在单机上用32位浮点比较了训练吞吐：PyTorch在所有基准上与最快框架的差距都在17%以内。例如ResNet-50每秒212张图（Chainer 219、MXNet 218、TensorFlow 200），GNMTv2翻译模型每秒15512个token（TensorFlow 9631）。作者把性能接近归因于各框架都调用同一版本的cuDNN和cuBLAS。采用情况方面，论文称ICLR 2019有296篇投稿提到PyTorch，并统计了自2017年1月首次发布以来arXiv论文中提及PyTorch的比例持续上升。

后来的发展

PyTorch之后在研究界被广泛使用：Hugging Face Transformers以它为主要后端，PyTorch Lightning、fastai、timm视觉模型库、Detectron2等生态建立在它之上，nanoGPT等教学代码也用它写成。2019年的TensorFlow 2与Eager也把eager执行设为默认。

后续版本补上了原设计的短板：PyTorch 1.0与TorchScript用TorchScript让模型脱离Python部署，PyTorch FSDP与TorchTitan提供大模型分布式训练，PyTorch 2与torch.compile的torch.compile在保持eager写法的同时捕获计算图、生成融合内核（借助Triton GPU编程语言）。2022年9月Meta宣布PyTorch改由Linux基金会旗下独立的PyTorch基金会管理。另一条路线JAX以函数式变换加整图编译与它竞争，在部分大模型训练中使用。

容易误解的地方

  • 动态图不等于没有图：反向传播用的图在每次前向时重新构建，用完即释放，所以每个iteration的结构都可以不同。
  • 因为GPU异步执行，用Python的time.time()直接测一个算子的耗时往往只测到排队时间，需要先torch.cuda.synchronize()。
  • 梯度默认是累加的，每步训练前要optimizer.zero_grad()，否则梯度会叠加到上一步上。

局限与后续

  • 逐个算子由Python调度执行，小算子多时解释器开销明显，也无法像静态图那样跨算子融合优化。
    后来针对它的工作　PyTorch 2与torch.compile JAX
  • 模型就是Python代码，部署到没有Python的服务器、手机等环境很不方便。
    后来针对它的工作　PyTorch 1.0与TorchScript ONNX模型交换格式 ExecuTorch 1.0
  • 初版只提供基本的多进程与通信原语，模型大到单卡放不下时的模型并行和参数切分需要用户自己实现。
    后来针对它的工作　Megatron-LM模型并行 ZeRO与DeepSpeed PyTorch FSDP TorchTitan
  • PyTorch本身不帮你写高性能GPU内核，注意力等新算子要么拼接多个现有算子（慢、费显存），要么手写CUDA。
    后来针对它的工作　Triton GPU编程语言 FlashAttention

它建立在什么之上

  • 使用
    NumPy与SciPy2006.10 · 系统·效率 已核对
    张量接口与NumPy相近，并可与NumPy数组零拷贝互转，融入Python科学计算生态。
  • 改进
    Theano与自动微分2010.06 · 系统·效率 已核对
    针对静态图框架（论文以Theano等为例）难用、难调试、可表达的计算类型受限的问题，用即时执行改善了易用性，同时靠工程优化让速度保持在最快框架的17%以内。
  • 改进
    Chainer与Define-by-Run2015.06 · 系统·效率 已核对
    沿用Chainer首创的define-by-run动态图和面向对象模型写法，论文明确称这一设计由Chainer和DyNet开创。
  • 延续
    Torch72011 · 系统·效率 已核对
    继承Torch7的张量库与模块化设计，把前端从Lua换成Python，并用引用计数替代Lua垃圾回收管理显存。
  • 使用
    Hogwild!并行SGD2011 · 系统·效率 已核对
    torch.multiprocessing透明地共享CUDA张量，使Hogwild!式的无锁异步训练很容易实现。
  • 使用
    cuDNN2014.09 · 硬件 已核对
    卷积等关键算子调用cuDNN和cuBLAS，这也是各框架单机性能接近的原因。
  • 竞争
    TensorFlow2015.11 · 系统·效率 待核对
    同一时期的主要竞争者：TensorFlow主打静态图与部署，PyTorch主打命令式易用；论文的单机测试中ResNet-50为212对200张/秒，GNMTv2为15512对9631个token/秒。
  • 延续
    autograd：给NumPy求导2015 · 系统·效率 待核对
    论文在背景中写到，autograd包让“运行时记录运算再反向求导”的技术在NumPy数组上流行起来；PyTorch采用了同一类运算符重载式自动微分。论文没有说直接使用了它的代码。
  • 改进
    Lisp语言1960.04 · 事件
    擅长符号结构，不擅长大规模数值数组运算，后来以矩阵计算为主的统计学习和深度学习基本没有用它。
  • 改进
    反向模式自动微分1970 · 系统·效率
    需要人为把程序整理成计算序列，没有能直接作用于普通源代码或数组程序的通用工具。
  • 改进
    OpenCV视觉库2000.06 · 系统·效率
    收录的是手工设计的流水线，每一步都要调阈值和参数，在复杂真实场景里的识别精度有明显上限。
  • 改进
    scikit-learn2010.02 · 系统·效率
    不支持GPU，也不做深度神经网络，图像、语音、文本等需要表示学习的任务很快被深度学习框架接管。
  • 改进
    Kaldi2011.12 · 语音
    C++加大量shell和Perl脚本，没有自动微分，研究新的神经网络结构要手写前向和反向，难以与PyTorch等框架结合。

    网络必须用配置文件描述成固定的层图，循环网络、动态结构和新运算很难表达，研究灵活性差。
  • 改进
    Speelpenning梯度代码生成1980 · 系统·效率
    当时是针对Fortran式程序的源代码变换，不能直接处理运行时才确定的控制流。
  • 改进
    MATLAB1984 · 系统·效率
    没有自动求导和GPU原生支持，深度学习时代被Python框架取代。
  • 改进
    R语言1996 · 系统·效率
    解释型语言速度较慢，内存里装下整个数据集，工程化部署和深度学习生态弱。
  • 改进

    高层封装让自定义训练循环和非常规结构较麻烦，需要时仍要下沉到后端。
  • 改进

读懂它需要的概念

自动微分与计算图 反向传播 随机梯度下降与小批量 CPU、GPU与并行计算 向量、矩阵与张量 显存、内存带宽与“内存墙”

本篇术语

  • eager执行　每条张量运算语句立即执行并返回结果，与先构建整张图再执行的静态图模式相对。
  • CUDA流　GPU上的任务队列。CPU把算子依次放进流里就返回，GPU按顺序执行，从而让CPU和GPU同时工作。
  • 缓存分配器　PyTorch自己管理的显存池：释放的显存不还给驱动而是留着复用，避免频繁调用代价高、可能阻塞的cudaMalloc/cudaFree。

怎么学

先会自动微分与计算图和反向传播。跟着官方Learn the Basics教程完成张量、自动微分、构建模型、训练循环四节。然后读论文第4节（以可用性为中心的设计）和第5节（性能相关的实现），对照理解为什么Python解释开销没有拖慢GPU。动手：手写一个两层MLP的训练循环在MNIST上跑通，再用torch.profiler看一次迭代里CPU调度和GPU计算的时间线。
