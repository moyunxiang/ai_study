LMCache KV缓存层

LMCache: An Efficient KV Cache Layer for Enterprise-Scale LLM Inference
2025.10论文延伸Yuhan Liu, Yihua Cheng, Jiayi Yao, Yuwei An, Xiaokun Chen, Shaoting Feng, Yuyang Huang, Samuel Shen et al. · 芝加哥大学, Tensormesh待核对
arXiv ↗GitHub ↗在交互版中打开（演化树、学习进度）

问题

用户累积的KV缓存早已远超GPU显存，推理引擎只能把它留在显存里、用完即丢，同一段长文档或多轮对话被反复重新预填充。

方法

在推理引擎之外做一个独立的KV缓存层：把vLLM、SGLang算出的KV搬到CPU内存、本地盘、远端存储里，再在不同请求、不同引擎之间按需取回。

影响

论文称是首个开源的KV缓存层，其连接器接口被NVIDIA Dynamo、llm-d、vLLM production stack等采用。

方法

Prompt Caching和SGLang与RadixAttention的前缀缓存都把KV留在GPU显存里，显存一满就要淘汰；预填充-解码分离部署式的预填充-解码分离又需要把KV从一台机器传到另一台。LMCache把这两件事统一成“KV缓存的存储与搬运”问题。

它做了三件事：一是高度优化的数据搬运，批量拷贝、计算与I/O流水线并行，逐层边算边存边取；二是一个模块化的KV连接器接口，分成调度器侧（查询已有多少token命中缓存）和执行侧（加载、保存KV）两组钩子，让LMCache不必跟着vLLM与PagedAttention内部实现的快速变化反复重写；三是一套控制API，可在GPU、CPU内存、本地盘、远端存储（Redis、S3、Mooncake以KV缓存为中心存储等）之间编排缓存。

论文称与vLLM组合时，在多轮问答、文档分析等负载上吞吐最多提升15倍。企业部署中还观察到：业界常用的“截断上下文只保留最新部分”会让前缀缓存命中率从约85%降到约45%。

局限与后续

  • 远端取回KV要占网络带宽，带宽不足时可能比重新预填充还慢，何时取、何时重算仍需按负载调。
    本站还没有记录针对它的后续工作（不代表没有人解决）

  • 竞争
    Mooncake以KV缓存为中心2024.06 · 系统·效率
    都以KV缓存为中心设计推理系统；Mooncake是Kimi的内部架构，LMCache是可插入开源引擎的独立层，且支持把Mooncake存储作为后端。

    Prompt Caching2024.08 · 系统·效率
    前缀缓存只在单机显存内复用，LMCache让复用跨请求、跨机器、跨引擎。
