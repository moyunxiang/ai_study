LLMCompiler并行函数调用

An LLM Compiler for Parallel Function Calling
2023.12论文延伸Sehoon Kim, Suhong Moon, Ryan Tabrizi, Nicholas Lee, Michael W. Mahoney, Kurt Keutzer, Amir Gholami · 加州大学伯克利分校待核对
arXiv ↗GitHub ↗在交互版中打开（演化树、学习进度）

问题

ReAct式智能体一次只调用一个函数，调用完再想下一步；彼此独立的多个查询（比如分别查两个人的年龄）也只能排队执行，延迟和费用都随步数累加。

方法

借鉴编译器：先让LLM把任务规划成一张函数调用的依赖图（DAG），后续步骤用$1、$2等占位符引用前面的结果；调度器把没有依赖的调用并行派发给执行器，结果回填后再继续。

影响

在多个基准上相比ReAct最多降低延迟3.7倍、费用6.7倍，准确率最多提高约9%；并行工具调用此后成为智能体框架（如LangGraph）和模型API的常见能力。

方法

三个组件：

  • 函数调用规划器：LLM一次写出全部任务及其依赖，例如问「微软和苹果谁的市值更高」，计划是 1. search(微软市值)、2. search(苹果市值)、3. compare($1, $2)。1和2互不依赖，3要等它们的结果。
  • 任务调度单元：按依赖关系找出已就绪的任务派发出去，并把$1、$2替换成真实结果。
  • 执行器：并行运行这些函数调用。

与ReWOO先规划后执行一样先写计划再执行，但ReWOO按顺序执行，LLMCompiler把计划看成图并行执行；对于Game of 24这类需要根据中间结果改变策略的任务，执行器的结果还可以回传给规划器做动态重规划。

作者在HotpotQA多跳问答、电影推荐、自建的ParallelQA、Game of 24和WebShop上，用GPT-3.5、GPT-4和Llama 2 70B实验，并与ReAct以及OpenAI当时新推出的并行函数调用对比。以HotpotQA为例，用GPT时比ReAct快1.8倍（3.95秒对7.12秒）、费用降低3.37倍；摘要报告的跨任务最大值为延迟3.7倍、费用6.7倍、准确率约+9%。

局限与后续

  • 计划质量完全依赖规划器一次性拆解任务的能力，拆错依赖关系会导致并行执行出错。

  • 使用
    函数调用成为标准接口2023.06 · 推理·智能体

  • 使用
    HotpotQA多跳问答2018.09 · 数据·评测
    主要评测基准之一。
  • 改进
    DecomP分解式提示2022.10 · 推理·智能体
    每个子任务都是一次单独的模型调用，调用次数随分解深度和输入长度增长，延迟与成本明显高于单次提示。
  • 改进
    Chameleon工具组合推理2023.04 · 推理·智能体
    工具序列一次规划完就照做，执行中发现结果不对也不会回头修改计划。
  • 延续
    ReWOO先规划后执行2023.05 · 推理·智能体
    同样先规划后执行并用变量引用未来结果，进一步把计划变成可并行的DAG并支持重规划。
