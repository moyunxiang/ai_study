思维骨架SoT并行生成

Skeleton-of-Thought: Prompting LLMs for Efficient Parallel Generation
2023.07论文延伸Xuefei Ning, Zinan Lin, Zixuan Zhou, Zifu Wang, Huazhong Yang, Yu Wang · 清华大学 / 微软研究院 / 鲁汶大学 / 无问芯穹待核对
arXiv ↗GitHub ↗在交互版中打开（演化树、学习进度）

问题

大模型逐个词元地生成，一个几百字的回答必须一个词一个词等下去；当时提速主要靠改模型结构或推理系统，很少有人从“回答怎么组织”这个角度想办法。

方法

像人写文章一样先列提纲：第一次调用只让模型写出答案的骨架（几个要点，每点几个词）；然后对每个要点同时发起一次调用（或在一个批次里并行解码）各自展开，最后把各段拼起来。

影响

在12个模型上取得最高2.39倍的端到端加速，并在不少问题类别上回答质量不降反升；把“让模型自己规划输出结构以便并行生成”变成一个研究方向，后来的并行思考与并行解码工作常引用它。

背景

自回归模型生成N个词元就要串行跑N次前向计算，回答越长，用户等得越久。已有的加速办法分两类：改模型（量化、剪枝、更高效的注意力）和改系统（推测解码、批处理调度）。作者提出第三条路：改数据层面——也就是改模型输出的内容组织方式。

方法

第一步：骨架。用一个固定的提示模板要求模型只写出回答的提纲，例如问“如何提高睡眠质量”，模型先输出“1. 规律作息 2. 卧室环境 3. 睡前少用屏幕 4. 适量运动”，每点只有几个词。

第二步：并行展开。对每个要点再构造一个提示：“原问题 + 完整骨架 + 请只把第i点写成一两句话”。对闭源API模型，同时发出多个请求；对开源模型，把这几个请求放进同一个批次解码。由于解码通常受显存带宽而非算力限制，批量多算几条序列几乎不增加单步耗时，于是总时间约等于骨架长度加上最长那一点的长度。

第三步：拼接。按序号把各点的展开连起来就是最终回答。

SoT-R：并非所有问题都适合先列提纲——需要一步步推导的数学、代码题，或答案本来就很短的问题，用SoT反而变差。于是加一个路由器（用LLM提示或训练一个小的RoBERTa分类器）判断问题是否适合，只对适合的问题触发SoT。

结果：在Vicuna-80等问题集上测了12个开源和API模型，最高加速2.39倍；用FastChat与LLMZoo的LLM评审比较，多数模型在通用、知识、常识等类别上回答质量持平或更好，数学、编程类明显变差。

后来的发展

它说明“输出的结构”本身可以被利用来换速度；之后关于并行推理分支、多路思考再汇总的研究（例如推理模型的并行思考）都延续了“先规划、后并行展开”的想法。

    同为降低生成延迟：投机解码在系统层面让小模型先猜，SoT在内容层面让模型自己安排可并行的结构。

读懂它需要的概念

自回归生成 解码：贪心、束搜索、温度与top-p 吞吐、延迟与批处理 显存、内存带宽与“内存墙” 上下文学习与提示

本篇术语

  • 批量解码　把多条序列放在同一次前向计算里一起生成；在显存带宽受限时，多几条序列几乎不增加每步耗时。
  • 路由器（router）　先判断问题类型，再决定走哪条处理路径的小模块。

怎么学

先理解自回归生成和吞吐、延迟与批处理 → 读原文第2节两段提示模板和第4节按问题类别的质量分析 → 动手：对同一个开放问题，分别测普通生成与“骨架+并发展开”的总耗时和回答长度。
