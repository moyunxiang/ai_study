# 阶段B：节点讲解规范（content）

## 读者是谁

**只有基本CS和数学基础的人**：会编程，学过微积分、线性代数、概率论的入门内容，但没有系统学过机器学习。目标是他只靠这个网站，按时间顺序读下来，就能完整入门AI研究——知道每个阶段大家在攻克什么、每篇工作解决了什么、留下了什么、后来谁接着解决。

所以每篇讲解必须**自己站得住**：读者不看原文也能明白这篇工作做了什么、为什么这么做。不能假设读者认识任何没解释过的术语。

## 你要读的文件

1. 本文件。
2. `data/content/llm/transformer.json` —— **范例，照这个标准和口吻写**。
3. `data/concepts.txt` —— 基础概念登记表（约190个）。正文里遇到这些概念时用 `[[c:key]]` 链接过去，不必自己从头解释。
4. `data/tracks.json` 里你负责的分支，以及 `data/eras.json`（知道每个时代的大背景）。
5. `data/skeleton/` 下全部文件（`*.txt` 和 `*.add.txt`）—— 节点登记表。你需要知道有哪些id可以引用。用 `grep` 查，不必逐行精读。

## 输出

你的任务清单里每个节点写一个文件：`data/content/<track>/<id>.json`（用Write工具）。**写完一个存一个**，不要攒到最后。不要修改任何别的文件。

如果文件已存在，说明别人写过了，跳过。

## 字段

```jsonc
{
  "id": "与文件名一致",
  "who": "主要作者（最多8位，多了写 et al.） · 机构",
  "venue": "NeurIPS 2017",              // 可选。发表处；产品/事件可省略
  "links": [{"label": "arXiv", "url": "https://…"}],   // 第一个是原始出处；可再放1–3个真正有助于学习的资料

  // —— 短字段：图上的卡片和列表里显示，每个一两句话，不超过约80字 ——
  "problem": "当时卡在哪里",
  "idea":    "它怎么解决的",
  "impact":  "它改变了什么",

  // —— 长讲解 ——
  "background": "背景：当时的主流做法是什么，具体卡在哪，为什么是个问题",
  "method":     "方法：核心机制，讲到读者能向别人复述。该有公式就给公式",
  "results":    "结果：关键实验和数字，在什么数据上比谁好多少",
  "legacy":     "后续：它直接催生了什么；今天还在用吗，哪些部分被替换了",
  "pitfalls":   "常见误解与注意点（可选，写成 - 列表）",

  // —— 连接：这张图的核心价值 ——
  "limits": [    // 它留下的、没解决的问题。每条一句具体的话
    {"text": "……", "solved_by": ["后来解决或明显缓解了这个问题的节点id", "…"]}
  ],
  "relations": [ // 它与**更早**节点的关系。每条都要写清楚具体是什么关系
    {"to": "更早的节点id", "type": "solves | extends | uses | rivals", "note": "一句话"}
  ],

  "prereq": ["读懂这篇需要先会的概念key，来自 data/concepts.txt，3–8个"],
  "terms":  [{"t": "本篇新出现的术语", "d": "一两句大白话解释"}],   // 概念表里没有、但本文用到的术语，0–5个
  "learn":  "怎么学：先补什么 → 读原文哪几节 / 看哪个资料 → 动手做什么",
  "check":  {"source": "你实际打开核对的URL", "confirmed": "核对了什么（标题、日期、哪个数字）"}
}
```

### 各tier的要求

| tier | 必填 | 正文（background+method+results+legacy）汉字数 | limits | relations |
|---|---|---|---|---|
| 1 主干 | 全部（pitfalls、venue除外） | 700–1200 | 3–5条 | 4–8条 |
| 2 重要 | results、learn、prereq 可省 | 400–700 | 2–4条 | 3–6条 |
| 3 延伸 | 只要 who、links、三个短字段、method、check；其余能写就写 | 150–350 | 1–2条 | 2–4条 |

tier 3 的 `method` 可以把背景、做法、影响合在一起写成两三段。

非论文节点（硬件、事件、数据集、系统、概念）同样用这些字段，含义相应调整：`background` = 当时的局面；`method` = 它是什么、关键规格/设计/经过；`results` = 关键数字（性能、规模、金额、用户数）；`legacy` = 之后的影响。

### relations 的四种类型

- `solves`：本节点**解决或明显缓解**了对方留下的某个具体问题。note写清是哪个问题、怎么解决的。这是最重要的一类，读者靠它看懂“谁解决了谁的问题”。
- `extends`：沿着对方的思路继续推进（做大、做深、推广到新场景）。
- `uses`：把对方当作一个部件拿来用。
- `rivals`：同一时期针对同一问题的不同路线。note写清分歧在哪、后来谁胜出。

骨架里已经给每个节点列了 `parents`。**每个parent都应该在你的relations里出现**，并补上类型和说明；此外再补充你认为重要的其他连接（跨分支的尤其要补）。relations只能指向日期不晚于本节点的节点。

### limits 与 solved_by

`limits` 写的是**这篇工作发表时确实存在的缺陷或遗留问题**，要具体（“采样需要1000步，生成一张图要几十秒”），不要空泛（“效果还有提升空间”）。

`solved_by` 填登记表里**更晚**的节点id。先用 `grep` 在 `data/skeleton/` 里找有没有对应的节点；找不到就留空数组或省略——留空表示“至今未解决或没有对应节点”，这对读者同样是有用信息。不要编造id，校验会报错。

最新的工作（2025年以后）的limits往往还没有人解决，这正是读者想知道的“当前开放问题”，认真写。

### 正文的写法

- 中文，书面但直白。**不要**写成论文摘要的翻译，也不要用“划时代”“里程碑式”“深刻影响”这类形容词——用事实和数字说明它为什么重要。
- 第一次出现的术语要么链接到概念（`[[c:softmax]]`），要么在 `terms` 里解释，要么在句子里用括号直接说明。
- 讲机制时用具体的例子或数字，而不是抽象描述。读者应该能据此向别人讲一遍。
- 公式写在反引号里，用Unicode字符，不用LaTeX：`` `L = −Σ y_i log p_i` ``。
- 可用的标记只有：空行分段、行首 `- ` 列表、`**粗体**`、`` `代码/公式` ``、`[[节点id]]`、`[[c:概念key]]`。不要用标题、表格、HTML、Markdown链接。
- `[[节点id]]` 会显示成那个节点的标题并可点击。提到任何登记表里有的工作时都用它，这是读者在图上跳转的主要方式。
- JSON字符串里**不要出现英文双引号**（会破坏JSON）；引用用中文引号“”或「」。换行写成 `\n`，分段写成 `\n\n`。
- 中文与英文、数字之间不加空格。

### 准确性（最重要）

- **每个节点都要打开原始出处核对**：标题、作者、日期，以及你在正文里引用的每一个数字。论文看arXiv abs页或正式发表页；产品看官方公告；事件看可靠的一手或主流媒体报道。把核对过的URL和内容写进 `check`。
- 数字必须来自你看到的页面。记不准、查不到的数字不要写，改成定性描述。
- 厂商的自我宣称写“官方称”。有争议的结论写明争议。
- 2024年以后的内容不要依赖记忆，一律联网核实。
- 如果发现骨架里的日期、标题有错，或者这个节点其实不该收，**不要改骨架**，在最后的回复里列出来。
- 搜索时只用主题关键词，不带任何个人信息。
- **不要用 WebSearch**：整个session共用的搜索额度已经用完，调用只会失败。核对一律用下面的工具（Bash里运行），它直接查公开接口，自带限速和重试：

```
python3 scripts/lookup.py arxiv 1706.03762 2005.14165     # arXiv官方记录：标题、作者、v1提交日期、完整摘要（可一次多个id）
python3 scripts/lookup.py title "Attention Is All You Need"  # 按标题找论文：日期、作者、venue、arXiv/DOI链接（不知道arXiv id时先用它）
python3 scripts/lookup.py wiki "Dartmouth workshop"          # 维基百科摘要：事件、硬件、机构、人物（第二个参数可写 zh）
python3 scripts/lookup.py url https://…                      # 抓取任意网页：标题、发布日期meta、正文前4000字（官方公告、博客）
python3 scripts/lookup.py news "关键词"                      # Google News：2025–2026年事件的报道标题、媒体、日期
python3 scripts/lookup.py hn "关键词"                        # Hacker News：发布公告的原始链接和日期
python3 scripts/lookup.py s2 "关键词"                        # Semantic Scholar：按关键词找论文
python3 scripts/lookup.py search "关键词"                    # 网页搜索，经常被限流，只作最后手段
```

  典型流程：论文节点 → `title` 找到论文（会同时给出摘要和arXiv链接）→ 需要确认arXiv首发日期时再用 `arxiv <id>`。**arXiv接口全局限速、很多agent共用，务必攒够8–15个id一次查完**（`lookup.py arxiv id1 id2 id3 …`），不要一个一个查。非论文节点 → `wiki` 或 `url` 打开官方公告。摘要里没有的数字，可以用 `url https://arxiv.org/html/<id>` 或 `url https://ar5iv.org/abs/<id>` 看正文；仍然查不到就不要写那个数字。
- WebFetch 如果可用也可以用来打开**已知URL**。接口限流时工具会自动退避；连续失败就换一种查法，不要跳过核对。

## 完成前自检

```
python3 scripts/build.py --check 2>&1 | grep "data/content/<你的track>/"
```

修掉所有指向你写的文件的 ERROR（非法JSON、缺字段、字数不足、引用了不存在的id、`[[…]]` 链接解析不了、relations方向反了）。别人文件的报错不用管。

## 最后回复

简短：写了多少个节点；哪些节点你没能核实所以没写或写得保守；发现的骨架错误（id、哪个字段、应该是什么、依据URL）；你认为这条分支还缺的重要节点。

# 概念词条规范（concepts）

如果你的任务是写基础概念词条：每个概念写一个文件 `data/concepts/<key>.json`，范例见 `data/concepts/softmax.json`。

```jsonc
{
  "key": "与文件名、登记表一致",
  "short": "一句话定义，40–80字",
  "body": "正文，300–700汉字",
  "example": "一个带具体数字的小例子（强烈建议）",
  "pitfalls": "常见误解（可选，- 列表）",
  "needs": ["先要会的其他概念key，0–4个"]
}
```

`body` 的写法：从“为什么需要它”讲起，然后给定义（必要时给公式），再说它在AI里出现在哪些地方，用 `[[节点id]]` 指向图上最典型的2–4个节点，用 `[[c:key]]` 指向相关概念。level 0 的概念当作读者第一次接触来写，但读者是会编程、学过大一数学的人，不需要从加减乘除讲起。标记规则与节点讲解相同。
