# 扩充收录规范（more）：继续补论文

## 背景

站点现在有三千多个节点，按“6个大方向 › 16条分支 › 主题线 › 节点”长成一棵树，每个节点都有讲解。站长的判断是**数量远远不够**：一个方向里读者会在综述、教材、related work里反复遇到的工作，还有很多没有收。这一轮只做一件事：**在你负责的那一条分支 `<track>` 里继续找没收的论文和工作，登记、归线、写讲解。** 不写研究思路，不补别名（除了新节点自己的 `aka`）。

轮次名 `<round>` 和本轮的侧重点、数量上限在任务说明里给你。

## 先读

- `guide/census.md`：分支边界表、登记表的7个字段、`date` / `tier` / `kind` / `parents` 的写法。
- `guide/content.md`：讲解文件的写法，**严格照它写**。范例 `data/content/llm/transformer.json`；再看两三篇本分支已有的 tier 3 讲解找篇幅和口气。
- `data/tracks.json` 里你的分支；`data/threads/<track>.json`（本分支的主题线和每个节点的归属）。
- 本分支全部登记表 `data/skeleton/<track>*.txt`，通读一遍，知道已经有什么。别的分支用 `grep` 查。

## 怎么找

按下面的顺序找，找够本轮的目标数为止。目标数不是硬线：已经核实并写好的节点，超出几个也留着，不要为了凑整删掉。

1. **上一轮留下的名单**：`data/_reports/` 里本分支以前各轮的报告（`more*-<track>.md`）的“下一轮还缺”一节，以及别的分支转给本分支的建议——运行 `grep -h "^- <track> |" data/_reports/more*-*.md`。这些名字和年份多数没核实过，逐条核实后再收；已经收了的跳过。
2. **现成的候选**：`data/_reports/_missing.md` 里本分支那一节还没收的。
3. **逐条主题线对账**：对本分支的每一条主题线，找一两份这个子方向的综述、教材章节、awesome list或课程大纲，把里面列出的工作和登记表对一遍，补上缺的。每条主题线都要过，不要只盯着最热的两三条。
4. **按年份对账**：这个子方向各年顶会的最佳论文、oral、时间检验奖；被引很高却没收的；2024–2026年被广泛跟进的新工作。
5. 任务说明里给的**本轮侧重点**优先于上面的顺序。

怎么查：**必须联网**。`python3 scripts/lookup.py`（见其帮助：`arxiv`、`title`、`s2`、`wiki`、`url`、`news`、`hn`、`search`）不占搜索额度，优先用它；也可以用 WebSearch / WebFetch。arXiv 接口全局限速，多个id一次查。

临时脚本和中间文件只放在任务说明给你的**专用临时目录**里。不要往共用目录里放通用名字的文件（`add.py`、`tmp.json` 之类）：别的agent在同时工作，上一轮出现过辅助脚本被别人覆盖、结果写进了别的分支文件的事故。

## 收录标准

比 `census.md` 宽，但每一个都必须是真实存在、你这次打开来源确认过的工作。

收：
- 综述、教材、课程里会列出来的方法、模型、系统、数据集；一个阶段里被广泛比较的强基线；
- 被后续工作直接建立其上的东西；定义了一个问题或一个说法的工作；
- 重要的负结果、争论、分析类论文；
- 2024年以后已经被多篇后续工作引用、比较或采用的新工作。

不收：
- 查不到原始出处、无法确认存在的；只在新闻标题里出现、没有论文也没有官方公告的；
- 同一想法的第N个小变体；只在某个榜上涨了一点、没有留下可复用想法的；
- 已经以别的id收过的（见下面“查重”）；
- 不属于本分支的（在报告里列出：名称、年份、建议分支）。

`tier` 绝大多数写3；确实是这个子方向的人都知道的写2；不要写1。

## 查重（很重要）

别的分支可能已经收了，别的agent也在同时写（各分支各轮的登记表都在 `data/skeleton/` 下）。动手写每个候选之前：

```
grep -rin "<简称>\|<官方标题里有区分度的一段>" data/skeleton/
ls data/content/*/<你想用的id>.json
```

id、短名、英文原题三样都要查；同一篇论文换个id再收一次是最常见的错误。登记那一刻**再查一次**。撞了就放弃你的那个（讲解文件、归属行都删掉）。

## 每个新节点做三件事（顺序不能反）

1. **写讲解**：`data/content/<track>/<id>.json`，按 `guide/content.md` 里 tier 3（或 tier 2）的篇幅。先打开原文（arXiv abs 或官方页面）再写；数字、作者、机构、日期只写这次打开的来源里确认过的，拿不准的数字改成定性的说法。`links` 里放原文链接（有arXiv的放arXiv abs链接）。你准备写进登记表的每个parent都要在 `relations` 里出现，带类型和一句说明；`limits[].solved_by` 指向登记表里真实存在的后续节点。可以多写一个字段 `"aka": ["缩写", "别名", …]`，放大家搜它时会用、但标题和英文原题里没有的叫法。
2. **归入主题线**：在 `data/threads/<track>.json` 的 `assign` 里加一行 `"<id>": "<已有的主题线key>"`。**不要**新增、删除、改名主题线，不要改动已有的归属。保持文件原有的排版，只插入行。节点的日期不能早于它所在主题线的起点（见该主题线的 `via` 节点的日期），否则换一条合适的线。
3. **最后登记**：在 `data/skeleton/<track>.<round>.txt`（新建；格式同其他登记表，一行一个，可以用 `#` 行分小节）里追加这一行。`parents` 给2–4个真实的继承关系，可跨分支，parent的日期不晚于自己；parent如果是你这一轮新加的，要先把那个parent做完并登记。

**登记行是最后一步，登记了就表示这个节点已经完整可用。** 主session会在你工作期间随时把已登记的节点构建上线，所以不要先登记后补讲解。一个节点做完再做下一个，不要攒到最后。

措辞克制：“首次”“第一个”“证明了”“取代了”只在来源明确这么说时才用。

## 不要做的事

- 不要改动已有的登记表、已有的讲解文件、`data/concepts.txt`、`data/tree.json`、`data/ideas/`、`data/aliases/`、任何脚本和前端文件。只能新建上面提到的文件，以及在 `data/threads/<track>.json` 的 `assign` 里插入行。
- 不要运行git命令，不要运行不带 `--check` 的 `scripts/build.py`。
- 向外部网站发请求时只用主题关键词，不要带任何个人信息。
- 站长本人尚未公开的工作**不得收录或提及**。具体是哪些，由主session在任务说明里单独告知，不写进仓库。

## 自检

```
# 在仓库根目录下运行
python3 scripts/build.py --check 2>&1 | grep -E "<track>\.<round>|threads/<track>|content/<track>/"
```

针对你写的文件的 ERROR 必须全部修掉；“官方标题相同，可能重复收录”的警告要逐条确认是不是真的重复，是就删掉你新加的那个。别的agent的文件报错不用管。

## 报告

把报告写到 `data/_reports/<round>-<track>.md`（新建，中文，不贴讲解内容），分这几节：

```
# <track> · <round> 轮报告（日期）

新增N个：id列表（tier 2的标出来），按主题线各补了几个。

## 没核实因此没写
## 凭一般了解写、没有逐项对照来源的地方
## 给别的分支
- <建议分支key> | 名称 | 年份 | 一句话说明          ← 每行一个，严格这个格式，方便别的分支grep
## 下一轮还缺
按主题线列具体名字和年份，越具体越好。
```

最终回复只要三四行：新增了多少个、有没有遗留的错误或需要主session处理的事、报告文件的路径。
