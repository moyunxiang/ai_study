# 主题线整理规范

站点的结构是四层：6个大方向 → 16条分支 → **主题线** → 节点。本规范说明怎样把一条分支里的全部节点整理成若干条主题线。产物会被画成一棵树：每条主题线是一根从母线分叉出来的枝，节点按时间排在枝上。

## 你要做的事

给定一条分支 `<track>`：

1. 读该分支的全部登记表：`data/skeleton/<track>.txt`、`<track>.add.txt`、`<track>.add2.txt`、`<track>.add3.txt`、`<track>.add4.txt`（存在的都读）。格式 `id | date | tier | kind | title | full | parents`。`.add.txt`里常有 `# --- 小节名 ---` 注释，是普查时的自然分组，**优先沿用**。以 `# PARENT`、`# SUGGEST`、`# FIX` 开头的注释行不是节点，忽略。
2. 读 `data/tracks.json` 里该分支的 `question`、`blurb`、`stages`，理解这条分支的叙事。
3. 对标题不足以判断归属的节点，读 `data/content/<track>/<id>.json` 里的 `problem` 和 `idea` 两个字段再决定，不要猜。
4. 写出 `data/threads/<track>.json`。
5. 运行 `python3 scripts/build.py --check 2>&1 | grep "threads/<track>"`，没有输出才算完成；有输出就按提示改到没有为止。

不需要联网，不要改登记表和讲解文件，只新建这一个文件。

## 文件格式

```json
{
  "threads": [
    {"key": "backbone", "name": "骨干网络", "blurb": "怎样设计一个通用的图像特征提取器，并把它做深、做快。", "from": null},
    {"key": "detection", "name": "目标检测", "blurb": "不只说图里有什么，还要框出在哪。", "from": "backbone", "via": "alexnet"}
  ],
  "assign": {
    "alexnet": "backbone",
    "rcnn": "detection"
  }
}
```

- `key`：小写字母、数字、连字符，分支内唯一。
- `name`：2–8个汉字为宜，最多12个字符宽度的中文（会显示在窄列里）。用名词短语，不带年份，不带“相关”“其他”这类空词。
- `blurb`：一句话，40字以内，说清这条线**在解决什么问题**，读者没学过也能看懂。
- `from`：这条线从本分支的哪条主题线分叉出来；直接从分支主干长出的写 `null`。只能指向本分支内的 `key`，不能成环。
- `via`（可选）：分叉点上的那个节点的id，即“没有它就没有这条线”的那个工作，可以是任何分支的节点，日期不能晚于这条线的第一个节点。拿不准就不写。
- `assign`：本分支**每一个**节点恰好归入一条主题线。
- `threads` 的顺序就是显示顺序：大致按起始时间排，分叉出来的线紧跟在它的母线后面。

## 怎么划分

- 每条分支 **6–12条** 主题线。每条至少3个节点；超过45个节点的线要考虑拆开。
- 一条主题线应该是“沿着同一个问题接力”的一串工作，读者顺着读下来能看到问题怎样一步步被解决。按**问题/技术路线**划分，不要按年代切段（年代由时间轴表达），也不要按机构划分。
- 允许有已经结束的线（例如“手工特征”“专家系统”），树上会画出它停在哪一年，这本身就是信息。
- tier 1 和 tier 2 的节点尤其要放对：它们在总览里最显眼。
- 实在归不进任何一条线的零散节点，放进与它最接近的线，不要设“杂项”线。
- 如果登记表的小节划分合理就直接用，太细（少于3个节点）就合并，太粗就拆。

## 自检

- `assign` 的键数等于该分支的节点数，没有多也没有少。
- 没有空的主题线。
- 随手挑5个 tier 3 节点，确认它们所在的线的 `blurb` 确实说的是它们在做的事。

## 报告

完成后只回报：主题线的 key、name、节点数；以及你拿不准归属的节点（最多10个，各一句理由）。不要贴出整个文件。
