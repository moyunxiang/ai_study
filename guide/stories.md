# 研究专题规范（stories）

## 是什么

专题是一篇**围绕一个问题、按时间把已有节点串起来的短文**，例如“Transformer为什么出现”。读者是会编程、学过大一数学、但没读过论文的人。他读完应该能向别人讲清楚：一开始大家卡在哪，每一步是谁往前推了什么，为什么是这个顺序，今天走到了哪。

专题不是论文列表。每一站都要回答“上一站留下了什么问题，这一站怎么回应的”，站与站之间靠问题连起来。

专题也不是新的知识库。**事实只来自已有节点的讲解**（`data/content/<track>/<id>.json`）和你这次核对过的来源；专题只负责把它们讲成一条线。

## 先做核对，再写专题

任务说明里会给你两份清单：

- **要核对的节点**：先按 `guide/review.md` 逐个做来源核对（改讲解、写 `data/review/<id>.json`）。这是主要工作量。
- **只读的节点**：专题里会用到，但由别的agent负责核对，你只读不改。

核对完之后再写专题，这样专题里的事实都是你刚对照过来源的。

## 文件

`data/stories/<key>.json`（key在任务说明里给定）：

```json
{
  "key": "why-transformer",
  "order": 1,
  "title": "Transformer为什么出现",
  "question": "2017年之前翻译模型已经很好用了，为什么还要把整个结构推倒重来？",
  "intro": "两三段。交代起点：当时的主流做法是什么，它卡在哪。不要预告全文。",
  "steps": [
    {
      "node": "seq2seq",
      "h": "把翻译变成一个网络的事",
      "text": "这一站做了什么、解决了上一站的什么问题、自己又留下了什么。100–220个汉字。可以用 [[节点id]]、[[c:概念key]]、**粗体**、`公式`。"
    }
  ],
  "takeaway": "一两段。这条线现在走到哪了；读者接下来可以读什么。",
  "caveats": "这条叙事线简化了什么、哪些因果是事后归纳而不是当事人的说法、哪些地方有不同看法。必须写，至少两句。",
  "figs": ["self-attention"],
  "next": ["gpt-and-bert"]
}
```

- `steps`：6–10站，按时间顺序。`node` 必须是登记表里的id；一个节点只出现一次。每站的小标题 `h` 是一句话说清这一站的作用，不是节点名。
- `text` 的第一句接上一站（“上一站的问题是……”），最后一句引出下一站（“但是……”）。最后一站除外。
- `figs`：可选，站内机制图的key（见 `data/figures/`，可能还没生成；只写任务说明里给你的）。
- `next`：可选，读完可以接着读的专题key（见任务说明里的专题总表）。
- `order` 用任务说明里给的数字。

## 写法

- 大白话。遇到术语，要么当场用一句话解释，要么链接到概念词条 `[[c:key]]`（key见 `data/concepts.txt`）。
- 讲机制，不只讲结论。“注意力让每个词直接看到所有词”要比“注意力效果更好”有用。
- 数字带条件，而且只用节点讲解里已有、你核对过的数字。
- **因果要克制**（和 `guide/review.md` 第3节同一套标准）：
  - 只有后一篇工作自己写明建立在前一篇之上，才能说“在……基础上”。否则说“之后”“同一时期”“采用了类似的想法”。
  - 不写“彻底解决”“完全取代”“证明了”。
  - 一个方向的转折往往有多个原因（数据、算力、方法），不要归给单独一篇论文。
  - 事后归纳的叙事要在 `caveats` 里说明它是归纳。
- 不要写“让我们来看”“值得注意的是”“总之”这类过渡话；不要在结尾升华。
- 中文与英文、数字相邻时不加空格（写“2017年”“用GPU训练”）。

## 自检

```
# 在仓库根目录下运行
python3 scripts/build.py --check 2>&1 | grep -E "stories/<key>|review/"
```

相关的 `ERROR` 必须修掉。

## 报告

在 `guide/review.md` 要求的报告之外，加两行：专题用了哪几站；`caveats` 里写了哪些简化。
