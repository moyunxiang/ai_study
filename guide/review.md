# 来源核对规范（review）

## 背景

站点有约3300个节点、约13000条关系边，讲解由AI模型撰写。写作时每个节点留了一条 `check`（一个URL加一句“核对了什么”），但那是写作模型自己的说法，**没有人或别的模型独立核对过**。网站要公开发布，需要一套诚实的审核状态：

| 状态 | 含义 | 谁能给 |
|---|---|---|
| 待核对 | 默认。没有任何审核记录 | — |
| 来源已核对 | 这一次**实际打开**了可靠的原始来源，逐项对照了讲解里的事实 | 你（按本规范做完之后） |
| 人工复核 | 真人核实过 | 只有真人。**你不能写这个状态** |

你的任务是对任务说明里列出的节点做“来源已核对”这一级的审核：逐个打开原始来源，对照讲解，改掉错的，降级说过头的，并留下可追溯的记录。

**宁可少给、不可错给。** 打不开来源、来源里找不到、只能凭记忆判断的内容，一律不算核对过。

今天是2026-11-22。

## 你能改、不能改的文件

- 能改：任务清单里那些节点的讲解文件 `data/content/<track>/<id>.json`（用Edit做最小修改，不要整篇重写）。
- 能新建：`data/review/<id>.json`（每个节点一个，见下）。
- 不能动：其他节点的讲解、登记表 `data/skeleton/`、`data/tree.json`、`data/threads/`、脚本、`docs/`。登记表里的日期、标题有错时写进审核记录的 `registry` 字段，由主session统一改。
- 不要运行git命令。联网时只用论文标题、arXiv编号这类关键词，不带任何个人信息。
- 站长本人尚未公开的工作不得提及。具体是哪些，由主session在任务说明里单独告知，不写进仓库。

## 每个节点怎么做

### 1. 读讲解，列出要核对的事实

读 `data/content/<track>/<id>.json` 全文，以及登记表里它那一行（`grep -rn "^<id> |" data/skeleton/`）。列出其中所有**可以被来源证实或证伪**的说法：

- 作者、机构、发表处、日期（登记表里的 `date` 和讲解里的 `venue`）。
- 所有数字：指标、数据集规模、参数量、训练成本、金额、用户数。
- “首次”“最早”“第一个”这类优先权说法。
- 方法描述里的关键机制（公式、结构、训练目标）。
- `results` 里的比较：在什么数据上、和谁比、好多少。

### 2. 打开原始来源

优先级：论文原文（arXiv摘要页 + HTML全文 `https://arxiv.org/html/<编号>` 或 ar5iv、ACL Anthology、会议官网、期刊页）> 官方公告和官方文档 > 作者主页 > 权威二手资料（教科书、综述）> 维基百科（只用来核对日期、人名这类基本事实）。新闻稿和博客只能核对“某件事发生了”，不能核对技术细节。

用WebFetch。提问时让它**原样摘出**你要核对的数字和句子，不要让它替你判断对错。一个来源打不开就换一个；都打不开就把这条记进 `unverified`。

可以用 `python3 scripts/lookup.py`（看 `--help`）批量核对arXiv的标题、作者、日期。

### 3. 对照，改讲解

| 情况 | 怎么办 |
|---|---|
| 和来源一致 | 记进 `checked` |
| 和来源不一致 | 按来源改讲解，记进 `changed`（写清“原来写的是什么，改成了什么”） |
| 来源里找不到，也找不到别的可靠来源 | 能删就删（不影响理解的细节），不能删就改成不带具体数字或限定语的说法，记进 `changed` 和 `unverified` |
| 属于评价而不是事实（“影响深远”“成为标准”） | 改成可以核对的说法，或加上限定（“截至2026年，多数……”），做不到就记进 `unverified` |

**说过头的措辞要降级**。这是这次审核的重点：

- “解决了”→ 如果后续工作只是缓解或改进，写“缓解了”“明显改善了”。只有问题确实不再存在时才写“解决”。
- “取代了”“淘汰了”“被放弃”→ 除非有明确依据，改成“在……上被……超过”“之后多数工作转向……”。
- “直接启发了”“催生了”→ 只有后一篇论文**自己写明**建立在前一篇之上（引用并说明），才能这么写。否则写“之后的……采用了类似的想法”。
- “证明了”→ 实验结果写“显示”“在……上表明”；数学证明才写“证明”。
- 实验数字必须带条件：在哪个数据集、和谁比、什么设置。“比之前最好的高2分”要能说出之前最好的是谁。
- 原论文的结论和后来的历史评价要分开：`results` 只写原论文报告的结果；后来的评价放 `legacy`，并且措辞要留余地。

改动要小：只改有问题的句子，保留原来的结构、口吻和 `[[链接]]`。格式和字段要求见 `guide/content.md`。

### 4. 核对关系（这张图的核心）

这个节点的每一条 `relations`（它与更早节点的关系）和每一条 `limits[].solved_by`（后来谁回应了它的问题）都要过一遍。判断标准：

- `solves`：后者针对前者的某个具体问题做了改进。**站内已经把这类边的显示名改成“改进”，不再叫“解决”**，但note里仍不能写“彻底解决”。后者的论文应当明确把这个问题当作动机。
- `extends`：后者沿着前者的思路往前推。需要后者引用前者并说明是在它基础上做的，或者同一团队的同一系列。
- `uses`：后者把前者当部件用。需要后者的方法里确实用了它。**用了相似的技术不算**。
- `rivals`：同一问题的不同路线。note不要写“谁胜出”，除非有明确依据；写清分歧在哪。
- **时间先后不等于因果。** 仅仅因为B晚于A、主题相近，不能说B建立在A之上。

每条关系给一个结论，写进审核记录的 `edges`：

- `ok`：来源支持，note不用改。
- `revised`：关系成立，但你改了类型或note（讲解文件里已经改好）。
- `weak`：说得通，但你没找到明确依据。保留，但站内会标“待核对”。
- 不成立的：**直接从讲解文件里删掉这条**（`relations` 里删掉该项，或从 `solved_by` 里删掉该id），并记进 `changed`。不要写进 `edges`。

`solved_by` 里的节点只需要核对“它确实针对这个问题”，不需要你去全面审核那个节点。

### 5. 给每条局限分类

`limits` 里每条局限，在讲解文件里按下面的规则加字段（都是可选的，不确定就不加）：

- `"stated": true`：原论文作者**自己在文中写了**这个局限（局限性小节、讨论、结论里），而且你这次在原文里看到了。
- `"open": "一句话依据"`：有可信依据表明这个问题到今天仍未解决（例如2025–2026年的综述或权威论文明确这么说）。依据里写清出处和年份。**没有依据就不要加**——`solved_by` 为空只说明本站没有记录后续工作，不说明问题没解决。

### 6. 写审核记录

`data/review/<id>.json`（做完一个存一个）：

```json
{
  "id": "transformer",
  "status": "source",
  "date": "2026-11-22",
  "by": "ai:claude-opus",
  "sources": [
    {"url": "https://arxiv.org/abs/1706.03762", "what": "摘要页：标题、作者、提交日期"},
    {"url": "https://arxiv.org/html/1706.03762", "what": "正文：第3节结构、表2的BLEU与训练成本"}
  ],
  "checked": ["8位作者及单位", "首次提交2017-06-12", "英德BLEU 28.4、英法41.8", "8块P100训练3.5天"],
  "changed": ["relations/convs2s 的note原写“卷积路线随后被放弃”，无依据，改为“之后的主流翻译系统多数转向Transformer”"],
  "unverified": ["legacy里“主体结构九年没变”属于评价，未找到可核对的来源"],
  "edges": {"bahdanau-attention": "ok", "seq2seq": "revised", "convs2s": "revised", "rope": "weak"},
  "registry": {}
}
```

- `sources`：只写这次**真的打开并读了**的。每条写清从里面核对了什么。至少一条。
- `checked`：逐项写，要具体到别人能复查（哪个数字、哪个日期）。至少三项。
- `changed`：没改就写 `[]`。
- `unverified`：仍然没法核对的说法。有就如实写，没有写 `[]`。
- `edges`：键是对方节点id，覆盖这个节点保留下来的全部 `relations` 和 `solved_by`。
- `registry`：登记表需要改的字段，如 `{"date": "2017-06"}`、`{"full": "正确的英文原题"}`；没有就写 `{}`。
- `status` 只能写 `"source"`，`by` 写 `"ai:claude-opus"`（或你实际的模型名）。

**如果一个节点的主要事实你核对不了**（原始来源都打不开，或来源与讲解出入太大需要重写），不要写审核记录，在最后的报告里说明。它会保持“待核对”。

## 自检

```
# 在仓库根目录下运行
python3 scripts/build.py --check 2>&1 | grep -E "ERROR" | grep -E "<你的节点id之一>|review/"
```

你改过的文件相关的 `ERROR` 必须修掉（最常见的是删关系时把JSON逗号弄坏、`solved_by` 指向不存在的id）。别人的文件报错不用管。

## 报告

简短，中文，不贴文件内容：

- 每个节点一行：id、审核结论（已写记录 / 未能核对）、改了几处、几条关系被删或改。
- 发现的**事实错误**清单（原来写的 → 来源里是什么）。
- 被删掉的关系清单（A → B，为什么不成立）。
- 登记表需要改的地方。
- 你认为还需要真人看一眼的地方。
